# puny-chat

> **혼자 또는 친구 한 명과 작은 Buddy를 키우면서 쓰는 초경량 1:1 실시간 채팅 앱.**
> Chat with someone you like, and raise a tiny buddy together. — **Chat first. Buddy makes it fun.**

무엇을 만들고 무엇을 만들지 않는지, 서버가 어떻게 동작하는지, 어떻게 운영하는지 적는다. 기능·범위·서버를 바꾸기 전에 읽고, 결정이 바뀌면
코드와 같은 커밋에서 고친다. 지금 상태만 적는다(지난 경위는 Git 기록에 있다).

# 제품

## 원칙

- **채팅은 핵심 기능, Buddy는 정체성.** 매일 쓰는 건 1:1 실시간 채팅이고, 다른 메신저와 다르게 만드는 건 둘이 함께 키우는 Buddy다.
  Buddy는 채팅 화면 위쪽 **무대**에서 살아 움직인다. Buddy 때문에 채팅 사용성을 희생하지 않는다.
- **레트로 Buddy, 현대적인 채팅.** 무대는 도트·제한된 색·작은 움직임, 채팅(메시지, 입력, 초대, 설정)은 익숙한 메신저처럼.
- **게임으로 만들지 않는다.** 퀘스트, 데일리 미션, 재화, 상점, 가챠, 장비, 전투, 미니게임, 랭킹, 친구 경쟁은 없다.
- **스트레스 없는 돌봄.** Buddy는 죽지 않는다. 방치하면 배고프고 더러워질 뿐이고, 돌보면 쉽게 돌아온다. 앱을 열라고 요구하지 않는다.
- **오리지널.** Pokémon·Tamagotchi·Digimon의 이름, 이미지, 캐릭터를 쓰지 않는다. 가져오는 건 배고픔·밥·똥·청소·성장·진화 같은
  virtual pet 아이디어와 도트라는 표현 방식뿐이다.
  - 피한다: 달걀형·원형 기기 테두리, 기기 버튼 3개, 흑백 LCD 위아래의 아이콘 줄, 특정 캐릭터를 떠올리게 하는 실루엣.
  - 써도 된다: 도트, 제한된 색, 작은 장난감 느낌, 알에서 시작하는 성장, 굵은 외곽선의 귀여운 캐릭터.
- **AI 기능은 넣지 않는다.** AI 채팅, 대화 요약, 데일리 질문 등. Buddy의 말은 정해진 문구와 확률로만 고른다.
- **수익화하지 않는다.** 광고·결제·후원이 없다. 붙이려면 그 전에 일본 전기통신사업 届出부터 한다(`docs/release.md`).
- **작게 출시한다.** 실제로 출시할 수 있는 작은 제품. 미래 기능을 위해 미리 추상화하지 않는다.
- 디자인 톤: Cute, Simple, Retro, Friendly.

## 핵심 경험

두 사람이 대화하면서 하나의 Buddy를 같이 키운다. Buddy 이벤트는 채팅 타임라인에 들어가고, 그 사이에서 대화가 생긴다.

```text
18:02  버디가 💩을 쌌어요
Henry: ㅋㅋ 또 쌌네
Yuki:  니가 치워
```

- **Solo → Duo.** 혼자 시작할 수 있고(room 멤버 1명), 친구를 초대하면 2명이 되며 Buddy는 그대로 이어진다. room은 최대 2명.
- **한 화면.** 헤더에 상대(접속·입력 중)와 도움말(물음표)·설정(톱니바퀴, `components/icons`), 그 아래 화면 높이의 약 1/3이 Buddy 무대, 나머지가 대화.
  하단 탭은 없다.
  - 무대는 입력 중에도, 위로 스크롤해도 접히지 않는다(접었다 펴면 손가락 아래에서 대화가 움직여 스크롤이 튄다).
  - 무대는 화면 폭을 꽉 채우고 아래를 바닥 선 색(`stageLine`)의 2px 줄로 닫으며, 그 아래 채팅 위로 옅은 그림자(`StageShade`)를 깐다(말풍선이
    방 밑으로 지나가는 느낌). 떠 있는 둥근 카드로 두면 대화가 그 밑으로 들어가는 것처럼 보인다.
- **입력하던 글.** 보내지 않은 입력은 사람·방별로 기기에 저장해(`features/chat/draft.ts`, 바뀔 때마다) 새로고침, 웹의 새 버전 불러오기,
  앱 종료 뒤에도 입력창에 남는다. 보내면 지우고, 로그아웃·계정 전환·계정 삭제 때 모두 지운다. 되살린 글로는 "입력 중"을 보내지 않는다.
- **푸시는 상대 메시지(와 친구가 처음 들어온 순간)용이다.** Buddy 상태로 알림을 보내지 않는다("배고파요!" 등).

## 처음 시작하기

- **흐름.** 시작하기 → 구경하기 → (위쪽 시작하기) → 이름 → Buddy 이름 짓기(알 탄생) → 혼자 채팅 화면 → 언제든 초대 링크·코드로 친구 초대.
- **코드로 시작.** 친구에게 코드를 받았으면 첫 화면의 "초대 코드로 시작하기": 4자리 코드 → 이름 → 그 코드로 바로 참가. 친구의 방에 들어가려면
  계정이 있어야 해서(아래 [게스트 우선](#게스트-우선)) 참가 화면이 Google·Apple 연결을 먼저 보여 주고, 연결하면 그 코드로 이어서 참가한다.
- **마지막 단계 전에는 계정이 없다.** 이름과 알 이름을 정하는 동안은 아직 서비스를 쓰는 것이 아니다(둘러보다 떠나는 사람이 많다).
  - 오는 길의 코드·이름·알 이름은 앱 메모리에만 둔다(`features/auth/start-flow`).
  - 마지막 단계(알 이름의 "버디 깨우기", 코드로 왔으면 이름의 "다음")에서 처음으로 Firebase 익명 로그인을 하고, 가드(`_layout.tsx`)가
    이름 저장 → 방 만들기 또는 그 코드의 참가를 이어서 한다(그동안 로딩 화면).
  - 그래서 오는 길의 뒤로가기는 그냥 화면 이동이고(입력한 것은 남는다) 빈 계정이 생기지 않는다. 알 이름 화면에는 "버디 깨우기"만 둔다.
- Google·Apple로 처음 로그인하면 이름을 묻지 않는다(App Store Guideline 4.0: Apple 로그인 뒤 이름·이메일을 다시 받지 않는다). Google은 토큰의
  이름으로 서버가 만들 때 넣고, Apple은 Apple 시트에서 받은 이름(처음 로그인할 때만 준다, `lib/social-auth`의 `onProfileName` → 시작 흐름의
  이름)을 가드가 저장한다. 이름을 받지 못하면 기본 이름(`name.fallback`, "친구")으로 두고 설정에서 바꾼다. 저장이 실패하면 이름 화면이 나오고,
  "← 처음으로"는 로그아웃해 첫 화면으로(`cancelStart`).
- **이용약관 동의.** 계정이 생기면(게스트는 "버디 깨우기" 직후, Google·Apple은 첫 로그인) 무엇보다 먼저 약관 화면(`features/terms/terms-gate`)이
  나오고 "동의하고 계속하기"를 눌러야 이름 저장·방 만들기로 넘어간다. 동의한 버전은 서버에 둔다(`termsAcceptedVersion`, 다른 기기에서 다시
  묻지 않는다). 약관이 생기기 전 사용자도 다음에 열 때 한 번 동의한다. 약관을 크게 바꾸면 `TERMS_VERSION`을 올려 다시 받는다.
- 방 없이 로그인한 사람(방을 나간 사람)은 알 이름 화면의 톱니바퀴로 설정에 가고, 친구 코드도 설정에서 넣는다.

## 구경하기

처음 온 사람(특히 포트폴리오로 보러 온 사람)은 혼자라 알 하나만 보인다. 그래서 첫 화면의 "시작하기"는 늘 먼저 구경하기(`/demo`)를 보여 준다.

- 로그인 없이 채팅 화면 그대로 대본이 재생되는 방이다(약 55초): 둘이 인사하면 함께 보너스로 알이 깨어나 춤추고, 밥을 먹고, 💩을 싸고
  친구가 치우고, 꼬마·어른으로 자란다.
- 방문자도 밥그릇·💩을 누르거나 메시지를 보낼 수 있다(상대가 정해진 문구로 짧게 답한다).
- 위쪽 막대의 "시작하기"는 채운 버튼으로 늘 보이고, 끝나면 어른 옆에 새 알이 놓이며 "바로 시작하기"로 이어진다.
- 앱 안에서만 돌고 계정·서버·저장이 없다.

## 게스트 우선

- **로그인이 시작을 막지 않는다.** 이름만 정하고 Firebase 익명 로그인으로 시작하며, 혼자 쓰는 기능은 게스트도 모두 쓴다. 짧은 시간에 게스트를
  여러 번 만들면 Firebase가 잠시 막는다(`auth/too-many-requests`): "잠시 뒤에 다시"로 알린다.
- **다른 사람과는 계정으로.** 친구 초대 코드 만들기, 친구의 코드로 참가, 꽉 찬 방에서 상대 자리를 잇는 코드는 Google·Apple을 연결한 사람만
  한다(서버 `ACCOUNT_REQUIRED`). 그래서 다른 사람과 나누는 대화는 모두 실제 계정끼리다. App Store가 익명 게스트끼리의 대화를 "익명으로 콘텐츠를
  올리는 앱"으로 보고 리젝했기 때문이다(Guideline 1.2). 앱은 그 응답을 받은 초대 시트와 참가 화면에서 연결 버튼을 보여 주고
  (`features/auth/components/account-required`), 연결하면 하던 일을 이어서 한다. 내 자리를 다른 곳으로 옮기는 코드(`/move`)는 같은 사람이라
  게스트도 쓴다. 이미 게스트끼리 연결된 방은 그대로 둔다.
- **게스트는 30일.** Firebase의 익명 계정 자동 정리(30일)를 그대로 제품 정책으로 쓴다. 기기를 바꾸거나 브라우저 데이터를 지우면 게스트
  계정은 되찾을 수 없다. 30일이 지나 계정이 지워진 뒤 같은 기기로 돌아오면, 첫 화면에서 예전 Buddy와 대화를 더 볼 수 없다고 알린다(앱이
  이 기기에서 쓰던 게스트의 생성 시각을 기억해 둔다). 만료된 게스트의 서버 데이터는 서버가 주 1회 지운다(아래 [게스트 정리](#게스트-정리)).
- **계정 연결.** 웹·아이폰 모두 Google·Apple. uid가 그대로라 Buddy·방·대화가 이어진다. 이미 다른 사용자인 계정이면 합치지 않고 확인 후
  전환한다. 문구는 "회원가입"이 아니라 "계정 연결".
- **알리는 곳.** 팝업으로 막지 않고 채팅 위를 가리지 않는다.
  - 첫 화면에서 30일을 알리고, 설정에 남은 일수와 계정 연결 버튼.
  - 무대의 **우편함**(`docs/fun-improvements.md`): 게스트인 동안 "기기를 바꿔도 대화를 이어가려면", 남은 날이 7·3·1일이 되면 그날의
    편지(계정 연결 버튼).
  - 같은 날 푸시도 보낸다(`account/GuestExpiryNotice`, 매일 19:00 일본 시간, 기기 언어로 한 번씩, 남은 날은 서버의 사용자 생성 시각으로
    앱처럼 올림).
- **게스트는 시작한 곳에만 있다.** 앱, 브라우저마다, 홈 화면 웹 앱(Safari와 저장 공간이 다르다), 카카오톡·LINE 같은 앱 안 브라우저가
  저장 공간이 따로라 다른 곳에서 열면 새 사람이 된다.
  - 설정의 계정 카드에 이 게스트가 있는 곳(이 앱, Safari, 홈 화면 앱, 카카오톡 안 브라우저 등, `features/auth/guest-place*`)을 적고,
    앱 안 브라우저면 계정 연결을 한 번 더 권한다.
  - 이미 쓴 초대 코드를 넣으면(`INVITATION_USED`) 새 코드를 받으라는 말과 함께, 그 방에 있던 사람이면 처음 쓰던 곳에서 열거나 상대에게
    다시 초대를 부탁하라고 알린다. 갈라진 사람은 [다시 초대](#room초대-규칙)로 잇는다.

## 화면

- **설정**(위에서부터): 프로필(이름 바꾸기), 계정(게스트 남은 날, 계정 연결), 화면(언어 기기 설정/한국어/日本語/English/繁體中文, 화면 모드 기기
  설정/라이트/다크), 알림(기기별 스위치, 웹은 여기서 브라우저 권한을 묻는다), 방 정보(생성일·버디 이름·함께하는 사람은 나를 뺀 상대,
  혼자면 "아직 혼자예요". 방 이름은 따로 없다), 방 이동(게스트의 "다른 브라우저에서 내 채팅방 참가", "초대 코드로 참가"), 서비스 안내
  (문의 및 신고, 개인정보처리방침, 이용약관. 버디 키우기 안내는 채팅 화면의 ? 아이콘에서 연다), 로그아웃, 계정 삭제(맨 아래).
  - 언어·화면 모드는 현재 값을 보여주는 행이고, 누르면 체크 표시가 있는 선택창(모바일 하단 시트, 넓은 웹 가운데 대화상자)을 연다. 이 기기에만 저장한다.
  - 설정은 계정이 생긴 뒤(이름을 정한 뒤)에 연다. 시작하는 길(구경하기·이름·알 이름)에는 설정이 없다. 방이 없을 때는 알 이름 화면의
    톱니바퀴로 연다(계정 삭제·로그아웃에 방이 필요 없다).
- **계정 삭제**는 두 번 묻는다(`features/auth/components/delete-account-dialog`): 먼저 지워지는 것과 남는 것을 보여 주고 "확인했어요,
  계속할게요", 이어서 마지막 "계정 삭제". 본인 메시지와 본인 이름이 든 시스템 기록을 지우고, 상대의 메시지·방·Buddy·앨범은 남긴다.
  일반 방 나가기는 대화를 남긴다. 서버 동작은 아래 [계정 삭제](#계정-삭제).
- **새 화면과 시트.** 설정에서 여는 것(내 채팅방 참가 코드 `/move`, 초대 코드로 참가, 문의 및 신고, 개인정보처리방침, 이용약관, 이름 바꾸기)은 모두
  새 화면이고 줄 끝에 `›`. 아래에서 올라오는 시트는 채팅 화면에서 잠깐 쓰고 닫는 것(친구 초대, 상대 시트, 우편함, 버디 상세)만.
- **뒤로가기.** 헤더의 뒤로가기는 늘 보인다(`components/header-back`). 기록이 없으면(웹에서 주소로 열거나 새로고침) 채팅, 로그인 전이면
  첫 화면으로 간다. 로그아웃·계정 삭제 뒤나 로그인 없이 막힌 주소를 열면 첫 화면(`sign-in`, `_layout.tsx`의 로그인 전 화면 중 맨 앞)으로
  간다. 웹도 아이폰처럼 제목은 가운데, 뒤로가기는 왼쪽의 둥근 버튼이고, 웹 주소가 바뀌어 브라우저 뒤로가기도 같다.
- 이름 바꾸기는 설정에서 연 경우(`edit=1`)에만 열리고, 그 밖에 이름 있는 사람이 오면 채팅으로 보낸다(시작한 뒤 브라우저 뒤로가기).

## 문의와 상대 신고

- 설정과 로그인 화면에서 문의·개인정보처리방침·이용약관(`/terms`)을 연다. 정책과 연락처(`support@puny-chat.com`)는 로그인 없이 공개하고 앱의 네 언어로 제공한다.
  이용약관은 부적절한 콘텐츠와 악의적인 이용자를 허용하지 않는다(무관용)고 밝히고, 신고를 24시간 안에 확인해 조치한다고 적는다.
  정책 화면에 따로 언어 버튼은 없고 앱 언어(설정, 없으면 기기 언어)를 따른다.
- 로그인한 사람은 문의 작성 화면을 쓴다. 상대가 있는 방에서만 "상대 신고"를 고를 수 있다. 답장 이메일 입력란은 없고, 접수 완료와 접수
  번호(화면에는 줄여서, 전체 UUID 복사 가능)를 앱에서 보여준다. 운영자에게만 메일 알림이 가고 사용자에게 개별 답장은 없다.
- **상대 시트.** 채팅 헤더의 상대 이름을 누르면 상대에 관한 일을 모은 시트가 열린다: 다시 초대, 신고하고 내보내기, 상대 내보내기, 방
  나가기(나만 조용히 빠지고 상대에게 방·버디·대화를 남긴다). 설정에는 방 정보만 두고 나가기·신고 버튼은 두지 않는다(신고는 "문의 및
  신고"에서도 된다). 혼자 방에는 나가기가 없다: 친구 코드로 참가하면 확인 후 저절로 나간다.
- **신고하고 내보내기**는 확인 후 상대를 퇴장시키고 **두 사람의 기존 대화 전체를 지우고** 기존 초대를 모두 무효화한다. 실행한 사람에게
  Buddy와 앨범이 남는다. 새 초대로 다시 연결할 수 있고, 차단 목록은 따로 없다. 서비스 전체 이용 제한은 운영자가 Firebase에서 계정을 막아서
  한다(아래 [접수 뒤 대응](#접수-뒤-대응)).
- 신고만 삭제 전 최근 메시지 최대 50개(사진은 보냈다는 표시만)를 운영자 검토용으로 90일 보관한다. 전용 관리자 페이지는 없다(운영은 Gmail과
  DB 콘솔, 아래 [운영](#운영)).
- **부적절한 말 가리기.** 서버가 텍스트 메시지를 저장하기 전에 금칙어를 글자 수만큼 `*`로 바꾼다(`chat/WordFilter`, 목록은
  `server/src/main/resources/chat/filtered-words.txt`). 상대·기록·푸시 미리보기 모두 가려진 글을 받는다. 심한 욕설·혐오·성적 표현·폭력 표현만
  네 언어로 짧게 두고, 흔한 말 안에 들어가는 낱말(시발점의 "시발", "보지 마"의 "보지" 등)은 넣지 않는다. 라틴 문자는 단어 단위, 한글·가나·한자는
  글자열로 찾는다. 이름과 사진은 가리지 않는다.

## 플랫폼

- **iOS가 기준이다.** Safe Area, 키보드, 스크롤, 백그라운드 복귀, 재연결, 중복 없는 전송, 읽음, 입력 중, 푸시 같은 작은 UX 품질이 중요하다.
- **Web은 보조.** 같은 모바일 레이아웃을 가운데 두고 최대 폭만 제한한다. 넓은 창(768px 이상)에서는 한 톤 어두운 배경 위의 폰 크기 틀로
  보인다. 링크를 공유하면 일본어 미리보기(제목, 설명, 온천 장면 이미지, `app/+html.tsx`)가 뜬다(일본 출시).
- Android는 나중에 같은 코드로.
- UI는 ja / ko / en / zh-Hant(번체 중국어, 대만). 기기 언어를 따르고, 지원하지 않으면 영어. 중국어는 간체 기기도 번체로 보인다(중국 본토에는
  출시하지 않는다). 주 대상은 일본 사용자.

# Buddy

Buddy 상태(레벨, 배고픔, 💩, 돌볼 수 있는지)는 서버가 계산한 `BuddyView`를 앱이 그대로 보여준다. 잠, 쓰다듬기, 춤·노래, 말풍선, 무대 꾸미기처럼
서버에 없는 모습은 앱이 정한다. 수치는 아래 [Buddy 규칙](#buddy-규칙), 볼거리의 자세한 내용은 `docs/fun-improvements.md`.

## 캐릭터와 그림

- **말랑이.** 동그란 떡 같은 몸에 머리의 식물이 자란다. 한 종류, 4단계로 머리 위 식물로 단계를 알아본다.

  | 단계 | 격자 | 모습 |
  | --- | --- | --- |
  | 알 | 16×16 | |
  | 아기 | 16×16 | 작은 새싹 |
  | 꼬마 | 20×20 | 잎 두 장과 팔 |
  | 어른 | 22×24 | 조금 더 크고 둥글게, 새싹 위에 벚꽃 |

- 동작은 단계마다 그린 기본 모습 하나에 눈·입·발만 바꿔 만든다. 모든 동작이 같은 얼굴이다.
- 도트는 문자열 격자 → SVG(`app/src/features/buddy/pixel`)로, 그림 하나는 색마다 경로 하나다(아이폰은 SVG 요소마다 네이티브 뷰라 요소 수가
  곧 무게). 비트맵이 없어 iOS·웹 모두 선명하다. 작은 격자, 적은 색, 굵은 외곽선, 머리가 큰 비율, 방향을 바꿀 때 좌우 반전, 프레임을
  뚝뚝 넘기는 움직임. 그림 작업 규칙은 `docs/fun-improvements.md`의 그림 작업.

## Buddy 무대

- **평소.** 무작위 위치로 좌우 이동한 뒤 1.5–5초 쉬고, 깜빡인다. 혼자 두면 20–40초마다 춤·노래나 가끔 생기는 사건을 한다. 꼬마·어른은
  방의 소품을 쓰기도 한다(오르골 켜고 춤추기, 창가에서 손님 기다리기, 금붕어 보기, 책 읽기).
- **잠.** 밤 23–7시(현지 시간, 라디오 DJ는 3–11시)에는 잔다. 상대 메시지가 오면 잠깐 깬다.
- **쓰다듬기.** 버디를 누르면 기뻐하거나(0.9초) 춤추거나 노래한다. 반응 중의 추가 클릭은 무시하고 쌓지 않는다. 채팅의 "춤"·"노래"와
  구경하기 대본은 클릭 잠금과 별개로 동작을 새로 시작한다. 예약된 자동 춤·노래는 진행 중인 반응을 덮어쓰지 않는다. 웹에서 마우스·터치로
  누를 때는 테두리를 그리지 않고, 키보드로 선택할 때만 포커스를 표시한다.
- **말하기.** 꼬마부터 머리 옆 말풍선으로 짧게 말한다(3초, 대화에는 남기지 않음): 3일 넘게 안 열었으면 "오랜만이야!", 그날 처음 열면
  시간대 인사, 밥·쓰다듬기에 "고마워!", 청소에 "개운해!", 배고프면 "배고파…", 배부를 때 밥을 주면 "배불러", 가끔 질문. 마지막으로 연
  시각은 기기에만 저장한다. 진화하는 동안은 말풍선을 띄우지 않는다.
- **방에서 일어난 일에 반응한다.** 실시간으로 받은 메시지로 시작하고, 앱을 다시 열거나 재연결해서 채운 메시지에는 반응하지 않는다. 누가
  했든 두 사람 화면에서 같이 보인다.

  | 일 | 무대 |
  | --- | --- |
  | 밥 | 냠냠 먹고 하트 |
  | 💩 | 힘주는 얼굴(> <)로 떨고 바닥에 💩 |
  | 청소 | 반짝이며 기뻐한다 |
  | 상대 메시지 | 폴짝 뛰며 머리 위에 "!" |
  | 레벨 업 | 머리 위에 "LV▲", 폴짝, 레벨 숫자 강조. 최고 레벨(60)에는 방이 반짝이고 하늘에서 빛기둥이 내려오며 안내 셋이 차례로 뜬다 |
  | 진화 | 금빛 고리가 퍼지는 동안 이전·새 모습이 번갈아 보이고(1.4초), 번쩍인 뒤 반짝이가 터지며 새 모습 |

  - 앱을 닫아둔 사이에 진화했으면 내 읽음 위치보다 새로울 때 다시 열 때 한 번 보여준다(최고 레벨도 같다, `missedMoment`).
  - 대화의 레벨 업 줄은 그 레벨에 소품이 오면 이름을 붙인다("Lv.2 ⬆️ 🎁 창문"). 20레벨이 넘으면 하루에 여러 번 올라도 그날의 가장 최근 줄만
    보인다(`timeline.ts`의 `foldLevelUps`, 메시지는 서버에 그대로 있고 무대는 매번 축하한다).
- **방 소품을 누르면** 저마다 움직이고, 화분·시계·창문·어항·좌탁·인형에는 버디가 한마디 한다(창문은 손님을 부르고, 장난감·라디오는 춤,
  오르골은 노래). EXP는 없다.
- **온천.** 무대 오른쪽 위 ♨ 버튼으로 온천에 가서 쉰다(이 기기에서만, 집 버튼이나 10분 뒤 돌아옴). 방에서 12시간 만이면 +3 EXP.
- **꿈.** 버디가 알인 동안 무대가 열릴 때마다(게임 오프닝처럼) 다 자란 모습의 짧은 꿈(약 10초, 누르면 건너뛴다)을 보여준다. 장면은 검은 원으로 바뀐다.
- **방의 빛.** 같은 방이 기기 시각에 따라 아침(살짝 푸르게)·낮·노을(창빛의 대비)·밤(무드등 둘레만 밝게)으로 칠해진다.

## 돌보기

- **식사.** 배고프면 알부터 머리 위에 밥 생각 풍선을 띄우고, 버디를 누르면 밥을 준다. 자는 동안 배고프면 같은 풍선이 연보라 꿈 구름으로 뜨고("배고파…" 말은 하지 않는다) 눌러서 밥을 줄 수 있다.
  - 아기는 오른쪽 화분 옆 밥그릇에서 먹는다(평소 밥이 있고, 배고플 때만 비어서 들썩이며 "!", 배부를 때 누르면 고개를 젓는다: 그림을 뒤집지 않고 몸을 좌우로 한 칸씩 흔든다).
  - 손이 생긴 꼬마·어른은 밥그릇이 없고, 먹을 때만 낮은 둥근 밥상이 나와 그 뒤에서 먹는다. 밥공기 색은 밥그릇 보상(파랑 → 은 → 금 → 도자기)을 따른다.
- **💩.** 누를 때마다 하나씩 사라진다(반짝이며 날아감). 마지막 하나를 치우면 대화에 한 줄. 버디 앞에 그려서 발밑에 있어도 누를 수 있다.
- **어른은 💩 대신 일.** 어른은 💩을 싸지 않는다. 직업 장치를 누르거나 채팅에 "일"을 보내면 장치로 가서 일하고, 1시간이 지났으면 +2 EXP와
  대화 한 줄이 남는다. 남은 시간은 보여주지 않는다.
- **채팅으로 돌보기.** 메시지 전체가 "밥"·"청소"·"똥"·"일"(과 각 언어의 같은 말)이면 그 돌봄을 한다. "춤"·"노래"면 춤추고 노래한다. 할 게
  없으면 "배불러", "이미 깨끗해!"로 답한다. 낱말 목록은 [Buddy 규칙](#buddy-규칙).
- **Buddy 상세.** 무대 왼쪽 위의 이름·레벨 타일(구석 버튼과 같은 바탕에 `›`, 눌러 볼 수 있게 보이도록)을 누르면 경험치, 배부름, 청결, 직업, 다음 보상, 함께 보너스, 직업이 생긴 뒤에는 오늘의 수다가 보인다. 밥·청소·일 버튼은 두지 않는다(무대의
  밥그릇·💩·직업 장치로 한다).
- **누르자마자 반응한다.** 밥그릇이나 💩을 누르면 서버를 기다리지 않고 바로 밥그릇이 차고 💩이 사라지며 버디가 반응한다(`use-buddy.ts`).
  - 요청은 뒤에서 차례로 보내(빠르게 여러 💩을 눌러도 동시 요청으로 거절되지 않게) 모두 답이 오면 서버 상태로 맞춘다. 실패하면 원래대로 돌아간다.
  - 내가 한 돌봄의 `FED`·`CLEANED`가 실시간으로 다시 와도 반응을 두 번 재생하지 않는다(`use-chat.ts`의 `playMine`).
  - 일과 온천은 서버가 정하는 일이라 그대로 기다린다.
- **모션.** 가장 자주 보는 모션이라 짧고 부드럽게(`buddy-stage.tsx`).
  - 밥 생각 말풍선은 몽글 커지며 나오고, 밥을 받으면 거품처럼 살짝 커지며 터진다(0.22초). "배고파…" 말은 그 자리에서 거둔다.
  - 꼬마부터의 밥상은 위에서 톡 내려앉고, 다 먹으면 빈 그릇으로 살짝 가라앉으며 사라진다.
  - 💩은 자리를 지키고, 누른 그 💩만 눌렸다 튀어 오르며 반짝 사라진다(0.46초). 상대나 채팅의 "청소"로 치워지면 끝의 것부터 사라진다.

## 성장

경험치(레벨)로만 진화한다. 레벨당 EXP는 **직업(Lv.10)까지 3·3·3·4·4·4·5·5·5, 그 뒤 10**. 공식은 사용자에게 보여주지 않고 "대화하고 돌봐줄수록 Buddy가
성장해요" 정도로만 말한다.

| 단계 | 누적 EXP | 많이 이야기하는 둘 | 가볍게 쓰는 둘 |
| --- | --- | --- | --- |
| 아기 (Lv.2) | 3 | 메시지 3개 | 메시지 3개 |
| 꼬마 (Lv.5) | 13 | 첫날 | 첫날 |
| 어른 (Lv.8) | 26 | 첫날 | 첫날 |
| 직업 (Lv.10) | 36 | 첫날 | 첫날 |
| 직업 바꾸기 (Lv.20, 이후 10레벨마다) | 136 | 약 3일 | 약 5일 |
| 최고·독립 (Lv.60) | 536 | 약 12일 | 약 3주 |

기간은 하루에 메시지 60개 또는 25개와 함께 보너스, 밥·청소·일·온천을 더해 직업 전에는 하루 약 85 또는 45, 직업 뒤에는 메시지 상한(하루 20)
때문에 약 45 또는 25 EXP를 번다고 가정한 대략의 값이다. 어른·직업에 볼거리가 몰려 있고 혼자 쓰는 사람도 첫 몇 분 안에 알이 깨는 것을
봐야 해서, 직업까지는 앞을 가파르게(레벨당 3에서 5로) 해 첫날 닿게 했다(메시지 상한도 없다). 그 뒤로는 하루 2–4레벨, 방 소품 두세 개씩이다.
직업 뒤에 레벨당 EXP를 늘리지 않는 것은 최고 레벨에서 독립하면 새 알로 다시 시작해서 아껴 둘 끝이 없기 때문이다.

- **직업 뒤의 메시지 상한 안내.** 직업이 정해지면 우편함에 편지가 와서 그 버디가 독립할 때까지 남는다(`grownUpLetter`: 버디 이름을 불러 "이제 똥도 안 싸고
  출근도 하는 번듯한 어른"이라고 축하하고, 이제 수다만으로는 천천히 자라고 밥·일·온천·둘이 함께로 쑥쑥 자란다고 알린다). Buddy 상세의 "💬 오늘의 수다"는 그날 메시지 EXP를 다 받았는지만 보여 주고 개수는
  보이지 않는다(`chatExpFull`). 도움말의 직업에도 한 줄. 매일 채팅에 알리거나 잠금 표시를 하지 않는다: 대화를 줄이게 하지 않으려고.

- **둘이 함께.** 같은 날 두 사람이 모두 메시지를 보내면 하루 한 번 +10 EXP. 대화에 "🤝 오늘은 둘 다 왔어요!" 카드, 무대에서 하트와 두 번
  크게 뛰기, 그날은 레벨 옆에 🤝. Buddy 상세에 "나 ✅ · 상대 ⏳"와 남은 일. 상대에게 메시지를 보내라는 알림은 보내지 않는다.
- **다음 목표.** 진화해서 새 모습이 자리 잡으면 무대 위쪽에 다음 목표가 4.5초쯤 뜬다: "Lv.2에 알이 깨어나요", "Lv.5에 꼬마가 돼요",
  "Lv.8에 어른이 돼요", 어른이 되면 "Lv.10에 직업이 정해져요. 둘이 한 일에 따라 달라져요!"(`buddy.nextStage.*`, 레벨은 앱 `api.ts`의 `NEXT_STEP_AT`).
- **직업.** Lv.10에 키운 방식에 따라 정해지고, Lv.20·30·40·50에 한 번씩 바꿔 다섯 직업을 모두 겪어 볼 수 있다. 규칙은 [Buddy 규칙](#직업),
  직업마다의 모습은 `docs/fun-improvements.md`의 직업.
- **Lv.20.** 대화에 "🔄 ○○이 Lv.20이 됐어요! 이제 직업을 바꿀 수 있어요" 카드(`GROWN`)가 남는다(어른은 Lv.8이라 "다 자랐다"고 하지
  않는다). 60까지는 방 소품이 레벨마다 계속 생긴다고 알린다. 버튼("🔄 직업 바꾸기")은 지금 바꿀 수 있을 때만 있고 Buddy 상세를 연다.
- **Lv.60.** 감사 카드(`MAX_LEVEL`, "💌 편지 읽기" 버튼은 우편함)가 남고, 무대에 빛줄기·깃털과 함께 안내가 차례로 뜨며 우편함에 감사의 편지가
  온다. 편지 아래의 "🎓 독립시키러 가기"가 Buddy 상세(이름 정하기)를 연다. EXP는 계속 쌓여 기록되지만 레벨과 바는 멈춘다.
- **독립과 앨범.** 독립은 **60에서만**이고 선택이라 계속 함께 지내도 된다(60까지 공들여 만든 소품을 건너뛰지 않게, 20에 "독립시키기"를
  내밀지 않는다). Buddy 상세(무대 이름 옆 🎓, 감사 편지의 버튼으로도 연다)에서 두 사람 중 누구든 확인 후 독립시킨다. 새 알의 이름을 지으면
  버디는 추억 앨범(이름, 함께한 기간, 직업)에 남고 무대에는 새 알이 온다. 앨범은 관계의 기록이지 수집 게임이 아니다.
- **우편함.** 무대 모서리 버튼(늘 보임)으로 여는 공지·편지함. 내용은 앱에 넣어 배포로 보내고, 읽음은 기기에 둔다(`docs/fun-improvements.md`의 우편함).
  작가 버디가 일하며 쓴 편지(직업 이벤트)도 여기로 온다. 이것만 서버가 남긴다. 다른 직업은 버디가 채팅에서 직접 말한다.

## 도움말과 안내 카드

- **도움말**(채팅 헤더의 물음표 아이콘, 설정): 돌보기, 자라기, 직업, 독립, 레벨 보상 순으로 설명한다. 레벨이 오르면 무엇이 바뀌는지를 늦게
  알게 되기 쉬워서, 큰 변화(Lv.10 직업, Lv.20부터 직업 바꾸기, Lv.60 독립)를 소품 목록보다 앞에 둔다. 소품 목록은 길어서 처음 5개만 보이고
  "보상 N개 더 보기"로 펼친다(그림은 펼칠 때 그린다). 설정·도움말 화면은 하나만 열린다(`dangerouslySingular`, 열리는 사이 다시 눌러도
  겹치지 않는다).
- **안내 카드.** 처음 들어오면(꿈이 끝난 뒤) 채팅 위에 안내 카드가 뜬다("10레벨이 되면 키운 방식에 따라 직업이 생기고, 최고 레벨 60까지
  키우면 독립…", `guide-banner.tsx`). 한 번 누를 때까지 들어올 때마다 보인다.
  - 카드 어디를 누르든(✕도) 카드가 닫히며 도움말이 열린다: 치우려고 누르는 그 순간이 나머지를 보여줄 때다.
  - 누른 기록은 사람마다 서버에 둔다(`guideSeenVersion`): 다른 기기·브라우저나 다른 방(계정 전환, 초대받은 방)에서도 다시 나오지 않는다.
    누르면 바로 닫히고 저장은 뒤에서 한다(실패하면 그 기기에 남겨 두었다가 다음에 서버로 올린다).
  - 카드 내용이 바뀌면 앱의 `GUIDE_VERSION`을 올려 모두에게 한 번 더 보인다.
- Buddy 상세에 "다음 보상: Lv.6 새싹 화분 · 2레벨 남았어요"가 보인다.

## 무대 꾸미기

성장 레벨(2·5·8)을 뺀 3–59의 모든 레벨에 하나씩(55개) 방이 조금씩 달라진다. 소품은 밀어내지 않고, 안 쓴 자리를 쓰거나 있던 것이 좋아진다
(`stage-decor.tsx`의 `REWARDS`, 서버가 준 레벨로 앱이 고른다). 소품마다의 레벨과 그림은 `docs/fun-improvements.md`의 방 소품.

- **화분**은 새싹(6) → 무성한 화분(13) → 꽃 핀 도자기(19) → 작은 나무(32) → 열매 달린 나무(45). 다음 화분이 오기 전까지 레벨마다 조금씩
  커진다. Lv.13 화분은 꽃 핀 선인장·고무나무·산세베리아·둥근 잎 화분 중 하나로 자란다. 버디 이름으로 정해서 두 사람 화면이 같고 다시
  열어도 그대로다.
- **밥그릇**은 은(9) → 금(10, 직업이 정해질 때) → 도자기(20, 첫 직업 바꾸기). 꼬마부터는 밥상의 그릇이 같은 색이다.
- **직업 무대 장치.** Lv.10에 직업이 정해지면 무대 왼쪽에 온다: 요리사 조리대, 정원사 큰 식물, 라디오 DJ 방송 책상, 작가 나무 책상,
  바리스타 카페 카운터. 장치는 늘 버디 앞에 있고 높이는 버디 입 바로 아래까지라 얼굴이 가려지지 않는다.
- **왼쪽 바닥.** 꼬마까지 비어 있는 자리에 나무 탁자(4)가 오고 그 위에 장난감(7)이 놓인다. Lv.10에 직업이 정해지면 직업 장치가 반짝이며
  그 자리에 온다(직업이 없는 어른은 장난감 그대로).
- **바닥과 벽.** 무대 가운데의 러그는 알일 때부터 깔려 있고 무늬가 바뀐다. 바닥은 마루, 다다미로 바뀐다. 벽에는 창문(하늘이 기기 시각을
  따른다)과 그 모서리의 덩굴 화분, 벽시계(뻐꾸기시계로 바뀐다)가 오고, 오른쪽 위 벽 선반(오르골·라디오·책, 52에 책이 가득한 선반), 창틀(인형·다육이·분홍 다육이), 무드등
  옆 협탁(어항), 가운데(좌탁)가 차례로 찬다. 창가 손님은 10가지.
- **철 따라.** 몇 가지는 기기 날짜로만 나온다(벚꽃잎, 풍령, 고추잠자리, 겨울의 코타츠, 설날의 가가미모찌). 레벨로 받고 철에만 꺼내며,
  이름에 기간을 붙인다.
- 새로 온 소품은 그 자리에서 반짝이며 나타난다(무대를 연 뒤 오른 레벨의 것만).
- **이사.** 독립하면 소품은 버디가 가지고 이사간다: 버디가 보따리를 메고 인사한 뒤 오른쪽으로 걸어 나가고, 원이 닫혔다 열리면 러그만 있는
  빈 방에 새 알이 있다(`buddy-scene.tsx`). 보상은 지금 버디의 레벨로만 정한다.
- **추억 앨범.** 독립시킨 버디는 벽에 걸지 않고 앨범에 모은다: 우편함과 온천 버튼 사이의 앨범 버튼(독립한 버디가 있을 때)으로 여는
  갤러리에 직업 모습으로 웃는 사진이 파스텔 액자에 걸린다(`album-gallery.tsx`).

# 서버

## 스택

- Java 25, Spring Boot 4.1, Gradle(Kotlin DSL), Spring WebFlux, Reactor, Spring Data Reactive MongoDB.
- 로컬은 Docker Compose의 MongoDB(`bootRun` 때 자동 실행). 테스트는 JUnit 5, Testcontainers(MongoDB), WebTestClient.
  Spring을 쓰는 테스트는 모두 `@FlowTest` 설정 하나를 같이 써서 컨텍스트와 MongoDB를 한 번만 띄운다. 클래스마다 설정·속성·빈 교체가
  다르면 컨텍스트가 따로 생겨 띄우고 닫는 시간이 늘어난다. 필요한 것은 `FlowTest`에 넣고, 데이터와 시계는 매 테스트 전 `CleanSlate`가 비운다.
- **Firebase ID token은 Admin SDK가 아니라 Spring Security reactive JWT로 검증한다.** Admin SDK의 `verifyIdToken`은 blocking이라서다.
  JWK set `https://www.googleapis.com/service_accounts/v1/jwk/securetoken@system.gserviceaccount.com`,
  `iss` = `https://securetoken.google.com/<projectId>`, `aud` = `<projectId>`, `sub` = Firebase uid. 사용자 식별은 항상 `sub`.

```text
history_deletions  계정 삭제 중 영향받는 방 id(삭제 진행 표식)
stats          { _id: "steps:<날짜>", ios|web|android: { welcome?, demo?, start?, name?, wake? } }
               { _id: "joined:<날짜>", joined?, d1?..d60? }
               { _id: "care:<날짜>", feed|clean|work: { chat?, tap? } }
               { _id: "visits:<날짜>", users? }   이용 통계(날짜는 일본 날짜, 사람별 기록 없음)
```

- **Buddy는 room에 embed한다.** room과 1:1로 생기고 지워지며 항상 같이 읽는다. 돌봄을 room 문서 하나의 atomic update로 처리한다.
- **트랜잭션·change stream·복잡한 aggregation에 기대지 않는다.** 동시성은 조건부 atomic update와 unique 인덱스로 해결한다.
- **멤버 최대 2명**: `updateOne({ _id, memberCount: { $lt: 2 }, memberIds: { $ne: uid } }, { $push: …, $inc: { memberCount: 1 } })`.
  수정된 문서가 없으면 가득 찬 것.
- **메시지 멱등성**: `{ roomId, senderId, clientMessageId }` unique 인덱스. 중복 키면 기존 메시지로 ack.
- **메시지 순서는 `_id` 하나로 정한다.** 히스토리(`{ roomId: 1, _id: -1 }`, `_id < cursor`), 재연결 복구, 타임라인 정렬, 읽음 위치가 모두
  같은 순서를 쓴다. 레플리카가 1개라 어긋날 수 있는 건 재배포 순간 같은 초에 만든 메시지뿐이다. 정확한 순서가 필요해지면 room별 sequence.
- **Buddy 상태는 조회 시점에 계산**한다(배고픔·💩은 `lastFedAt`·`lastCleanedAt`과 현재 시각). 스케줄러가 없다.
- 한 사용자는 room 하나에만 속한다(`users.roomId`).
- 새 필드는 기존 문서에 없으므로 nullable로 두고 없는 경우를 처리한다. 인덱스는 모듈별 `*Indexes` 클래스에서 명시적으로 만든다.

## WebSocket 프로토콜

`wss://<host>/ws`. 브라우저 WebSocket은 헤더를 못 붙이므로 **첫 메시지로 인증**한다(token을 URL에 넣지 않는다). 서버가 먼저 `hello`를
보내고 클라이언트는 그 뒤에 `auth`를 보낸다(업그레이드 직후 보낸 프레임은 사라질 수 있다). 5초 안에 인증이 없으면 끊는다.

```text
client → server
  { type: "auth", token }
  { type: "send", clientMessageId, text }
  { type: "typing", typing }                      입력 중이면 3초마다 다시
  { type: "read", messageId }                     화면에 보이는 가장 최근 상대 메시지(또는 Buddy 이벤트)
  { type: "pet" }                                  쓰다듬기. 저장하지 않고 상대에게 전달만
  { type: "react", messageId, reaction }          텍스트·사진 메시지에 반응(LOVE | LIKE | CHECK | WOW | SAD, null이면 뗀다)
  { type: "ping" }

server → client
  { type: "hello" }
  { type: "ready", userId, roomId, online, reads, historyVersion }
  { type: "ack", clientMessageId, message }       내 메시지 저장 완료(재전송이어도 같은 응답)
  { type: "message", message }                    상대 메시지, Buddy 이벤트, 사진(보낸 사람의 기기 포함 방 전체에)
  { type: "member", userId, displayName }         친구가 참가(solo → duo)
  { type: "left", userId }                         친구가 나감(duo → solo)
  { type: "historyChanged", historyVersion, deletedUserId }  계정 삭제·다시 초대로 기록이 바뀜. 다시 읽는다
  { type: "buddy", buddy }                         Buddy 상태 변경
  { type: "typing", userId, typing }              다른 멤버에게만. 6초 동안 안 오면 앱이 지운다
  { type: "presence", userId, online }            그 사용자의 첫 연결이 열리거나 마지막 연결이 닫힐 때
  { type: "read", userId, messageId }             읽음 위치가 앞으로 움직였을 때만
  { type: "pet", userId }                          상대가 쓰다듬음. 다른 멤버에게만
  { type: "reaction", message }                   반응이 바뀐 메시지(저장된 반응 전부). 반응한 사람의 기기를 포함해 방 전체에
  { type: "error", code }
  { type: "pong" }
```

| 에러 | 연결 | 상황 |
| --- | --- | --- |
| `UNAUTHORIZED`, `AUTH_TIMEOUT`, `ROOM_NOT_FOUND` | 끊음 | 인증 실패, 5초 안에 인증 없음, 방 없음 |
| `TOKEN_EXPIRED` | 끊음 | 토큰의 `exp`가 됨. 앱이 새 토큰으로 다시 연결한다 |
| `SEAT_TAKEN` | 끊음 | 다시 초대 코드로 다른 곳에서 이 자리에 들어옴. 앱이 알리고 방 없는 화면으로 |
| `INVALID_MESSAGE` | 유지 | 빈 문자열, 2000자 초과 |
| `MESSAGE_RATE_LIMIT` | 유지 | 보내기 제한(`clientMessageId` 포함) |
| `INVALID_EVENT`, `INVALID_REQUEST` | 유지 | 모르는 이벤트, 잘못된 값 |

### 연결

- 토큰은 연결할 때 한 번 확인한다. 즉시 폐기는 토큰 수명(1시간)만큼 늦는 걸 허용한다.
- 연결은 인증 시점의 room에 묶인다. room이 바뀌면 앱이 다시 연결한다. 한 연결의 이벤트는 순서대로 처리한다.
- 세션·presence·typing은 서버 메모리에만 둔다(재배포하면 사라진다). presence는 연결로 계산하고 기기 여러 대는 하나로 본다.
- 유휴 연결 타임아웃 때문에 서버가 25초마다 ping 프레임을 보낸다. 앱의 `ping`은 처리 중인 이벤트를 기다리지 않고 DB도 읽지 않고 바로
  `pong`으로 답한다(연결이 살아 있는지를 보는 것이라 서버가 바쁜지와 섞지 않는다).

### 끊김 감지와 재연결

- **끊김 감지**(`lib/realtime-socket.ts`): 네트워크가 사라져도 close 이벤트는 한참 늦을 수 있어 앱이 직접 확인한다.
  - 서버에서 20초 동안 아무 프레임이 없거나 무언가를 보낸 직후 `ping`을 보내고, 8초 안에 어떤 프레임도 오지 않으면 끊긴 것으로 보고 새로 연결한다.
  - 연결 후 15초 안에 `ready`가 없어도 같다.
  - 재연결 대기는 1초부터 두 배씩 최대 10초.
  - 웹은 브라우저의 `online`이면 바로 연결하고 `offline`이면 확인한다. 아이폰은 네트워크 변화를 듣지 않고(네이티브 모듈이 필요) 앱이 앞으로
    오거나 메시지를 보낼 때 대기 없이 다시 연결한다.
- **재연결 복구**(`features/chat/message-sync.ts`): REST로 연속해서 확인한 마지막 메시지 이후를 `after`로 채운다.
  - 실시간 메시지는 화면에 바로 합치되 복구 커서는 움직이지 않는다. 페이지가 성공하면 커서를 전진, 실패하면 그 위치에서 3초 뒤 다시(요청 제한 15초).
  - 한 번에 하나만 돌고, 재연결·종료 때 진행 중인 요청을 취소한다. 복구 중에는 읽음을 보내지 않는다.
  - ack 못 받은 메시지는 `ready`에서 같은 `clientMessageId`로 바로 다시 보낸다. 보내지 못한 메시지는 메모리에만 있어 앱을 끄면 사라진다.

### 읽음과 반응

- **읽음**은 앞으로만 움직인다: `messageId < 새 id` 조건부 upsert. 첫 읽음이 동시에 와서 중복 키가 나면 같은 조건으로 한 번 더 update한다.
  앱은 상대가 읽은 위치 이하인 내 메시지 중 가장 최근 것에 "읽음"을 표시한다.
- **반응**: 텍스트·사진 메시지를 길게 누르면(웹은 마우스를 누르고 있으면) 말풍선 위에 ❤️ 👍 ✅ 😮 😢이 뜬다.
  - 한 사람이 메시지 하나에 하나만 단다. 고른 걸 다시 누르면 떼고, 다른 걸 누르면 바뀐다. 내 메시지에도 달 수 있다.
  - 달린 반응은 말풍선 아래에 종류마다 칩(이모지와 개수)으로 보이고(내가 단 칩은 강조), 먼저 달린 종류가 왼쪽이고 새 종류는
    오른쪽에 붙는다(서버가 사람마다 처음 단 자리를 그대로 두고, 바꿔도 자리는 그대로다). 내 칩을 누르면 바로 떼고, 상대 칩을 누르면
    고르는 창이 열린다. 떼어진 칩은 바깥쪽으로 밀리며 흐려지고 옆 칩이 그 자리로 다가온다(`message-bubble.tsx`, `/preview`의 reaction chips).
  - 웹도 앱처럼 페이지의 글자 선택과 iOS Safari의 길게 누르기 메뉴를 막아(입력 칸과 `selectable` 글자는 예외) 길게 누르기가 반응만 연다.
  - 서버는 `reactions.<userId>`를 조건부 `$set`/`$unset`(같은 방의 TEXT·PHOTO만)으로 바꿔 끝 상태를 저장하므로 같은 요청이 두 번 와도 같다.
  - 앱은 바로 그려 두고 `reaction`으로 받은 저장 상태로 맞춘다. 끊겨 있으면 보내지 않는다. 재연결 복구는 새 메시지만 읽으므로, 다시 연결되면
    최신 페이지를 한 번 더 읽어 이미 보이는 메시지의 반응만 고친다.
  - 푸시는 보내지 않고 Buddy도 반응하지 않는다.

### 보내기 제한

`chat/SendLimiter`, 한 사람 기준(UTC 날, 서버 메모리라 재배포하면 다시 센다):

| 종류 | 1분 | 하루 | 넘으면 |
| --- | --- | --- | --- |
| 텍스트 | 120개 | 3,000개 | `error`(`MESSAGE_RATE_LIMIT`). 재전송도 센다(여유가 충분하다) |
| 사진 | 10장 | 200장 | 429 `PHOTO_RATE_LIMIT`. 이미 저장된 것의 재시도는 세지 않는다 |

둘이 대화하는 양보다 훨씬 많아 고장 난 클라이언트나 DB를 채우려는 경우만 걸린다. 앱은 그 메시지를 실패로 보여 "다시 보내기"를 둔다.
익명 게스트를 여러 개 만드는 것까지 막지는 않는다.

## 사진

1:1 대화에서 사진은 대화 자체라 한 장씩 보내는 것만 둔다. 여러 장, 카메라 촬영, 설명 글, 동영상, 기기에 저장, 확대는 없다.

- **보내기**: 입력창 왼쪽의 사진 버튼으로 앨범에서 한 장 고른다(아이폰은 시스템 사진 선택기라 사진 권한을 묻지 않는다, 웹은 파일 선택).
  - 앱이 긴 변 1600px JPEG로 줄여(`features/chat/photo-resize*.ts`, iOS 사진의 방향도 이때 펴진다) `POST /api/rooms/me/photos`로 올린다.
    원본은 올리지 않으므로 8MB짜리 사진·스크린샷도 그대로 고르면 된다.
  - 웹은 원본 크기의 canvas를 만들지 않고 이미지를 바로 목표 크기 canvas에 그린다(아이폰 Safari는 canvas 넓이에 상한이 있어 2,400만 화소
    사진을 원본 크기 canvas에 그리면 실패한다).
  - 고른 사진은 바로 말풍선(흐리게)으로 보이고, 실패하면 "다시 보내기"로 같은 `clientMessageId`로 다시 올린다. 연결이 없어 실패했으면
    텍스트처럼 다시 연결될 때(`ready`) 저절로 다시 올린다. 올리기 전의 사진은 메모리에만 있어 앱을 닫으면 사라진다.
  - 읽을 수 없는 파일(Windows 브라우저의 HEIC, 손상된 파일)을 고르면 "사진을 보낼 수 없어요"를 띄운다.
  - 올린 뒤에는 서버 사본을 미리 받아 그쪽으로 바꾸고 고른 파일을 놓는다.
  - 사진 모듈(`expo-image-picker`·`expo-image-manipulator`)이 없는 예전 아이폰 빌드에서는 버튼을 숨긴다.
- **서버**(`chat/ChatService`, `PhotoStore`): 같은 `clientMessageId`의 메시지가 있으면 그대로 돌려준다.
  - 이미지를 읽어(크기를 먼저 보고 4096×4096이 넘으면 거절, 저장 크기 아래로는 내려가지 않게 솎아 읽어 384MB 힙을 지킨다) 긴 변 1600px로
    줄이고 WebP(손실, 품질 80)로 다시 만든다. 키우지는 않는다. 1600px은 아이폰에서 세로 사진을 전체 화면으로 볼 때 필요한 약 1570px에 맞춘
    값이다(카카오톡·LINE의 기본 전송 크기도 1440–1480px 정도). 메타데이터(위치 등)는 남지 않는다.
  - 디스크 `<사진 폴더>/<roomId>/<photoId>.webp`에 쓰고 `PHOTO` 메시지(`photo { id, width, height }`)를 넣는다. 메시지 저장이 실패하면 새 파일을
    지우고, 동시 재시도로 중복 키가 났으면 먼저 저장된 메시지를 준다.
  - 인코딩은 CPU를 쓰는 blocking 작업이라 전용 스케줄러(동시 2개)에서 한다. WebP 인코더는 `webp-imageio`(libwebp 네이티브 포함).
- **전달**: 텍스트처럼 방 전체에 `message`(보낸 사람의 기기 포함, 앱은 `clientMessageId`로 합친다), 3초 뒤 읽지 않은 상대에게
  푸시("사진을 보냈어요"), 메시지 EXP +1과 둘이 함께. 돌보기 낱말·사랑 낱말은 세지 않는다. Buddy는 상대 메시지처럼 반응한다.
- **보기**: 말풍선 안에 사진(폭 최대 220pt, 비율은 `width`·`height`), 누르면 전체 화면(아무 데나 누르면 닫히고 왼쪽 위에 뒤로 가기
  화살표), 길게 누르면 반응.
  - 주소는 `<API 주소>/photos/<roomId>/<photoId>.webp`이고 앱이 메시지로 만든다. 웹의 `<img>`가 토큰을 붙일 수 없어 **토큰 없이** 주고, 대신
    `photoId`를 추측할 수 없는 128비트 난수로 둔다(주소를 아는 사람만 볼 수 있다). `Cache-Control: private, max-age=31536000, immutable`.
- **지우기**: 방이 지워지면(혼자 나가기, 신고·내보내기, 참가하며 두고 온 방) 그 방 폴더를 지운다. 계정 삭제·게스트 정리는 본인이 보낸 사진
  파일을 메시지보다 먼저 지운다(다시 해도 같다). 지운 사진의 주소는 404. 사진은 DB 백업에 들어가지 않고, 인스턴스 일일 스냅샷에만 최대
  7일 남는다(아래 [백업](#백업)).
- **용량**: 한 장 약 250–400KB. 말풍선도 같은 파일을 받는다(사진이 많아 데이터가 문제되면 말풍선용 썸네일을 따로 만든다). 디스크 남은
  공간이 5GB 아래면 받지 않는다(`PHOTO_UNAVAILABLE`, `buddychat.photos.min-free-space`).

## Buddy 규칙

수치는 `buddy/BuddyRules.java`, 주기는 서버 설정 `buddychat.buddy.*`(`full-to-empty` 150분, `poop-every` 1시간). 레벨 곡선은 코드(`BuddyRules.CURVE`)에 있다.
테스트는 숫자 대신 `BuddyRules.hungryAfter()`, `poopEvery()`로 시간을 보낸다. "하루"는 모두 일본 날짜다.

앱은 `BuddyView`를 그대로 보여준다: `name`, `exp`, `level`, `stage`, `levelProgress`, `fullness`, `poops`, `hungry`, `canFeed`, `canClean`,
`grown`(독립할 수 있음), `talkedToday`, `togetherToday`, `chatExpFull`, `job`, `leaning`, `canChangeJob`, `jobChangeAt`, `gifts`(직업 이벤트, 최근 것부터).

### 돌봄

| 돌봄 | 규칙 | EXP |
| --- | --- | --- |
| 밥 | 먹은 뒤 150분에 걸쳐 배부름 100 → 0. 80 미만(30분 뒤)이면 줄 수 있고, 30 이하(1시간 45분 뒤)면 배고프다 | +2 |
| 💩 | 바닥이 깨끗해진 뒤(`lastCleanedAt`) 1시간마다 하나, 최대 3개. 누를 때마다 하나씩 치운다(`poopsCleaned` 증가, 마지막 하나면 `lastCleanedAt`을 지금으로 옮겨 새 주기). 어른은 💩이 생기지 않는다 | 하나에 +2 |
| 일 | 어른만. 언제든 할 수 있지만 EXP와 타임라인 `WORKED`는 `lastWorkedAt`에서 1시간이 지났을 때만 | +2 |
| 온천 | 알이 아니면. 앱이 온천에 들어설 때 보낸다. EXP와 `BATHED`는 `lastBathedAt`에서 12시간이 지났을 때만(방에 하나). 온천에 있는지는 저장하지 않는다 | +3 |
| 메시지 | 텍스트·사진 하나. 직업(Lv.10) 전에는 상한이 없고, 그 뒤에는 방마다 하루 20까지(그날의 개수는 직업 전에도 센다) | +1 |

- **직업 이벤트**(`docs/fun-improvements.md`). 직업이 있는 버디가 일하면, 일을 시킨 사람의 지난 이벤트가 사흘(`GIFT_EVERY_DAYS`, 일본 날짜)
  전보다 오래됐을 때 그 사람에게 이벤트를 하나 연다. EXP의 1시간 주기와 따로, 사람마다 센다. `buddy.giftDays.<userId>`(마지막 날)가
  최근 사흘에 없을 때만 바꾸는 조건부 update 하나라 동시에 눌러도 하나.
  선물 `{ id, to, job, pick, at }`(`pick`은 0–999, 무엇인지는 앱이 고른다)은 `buddy.gifts`에 마지막 30개(`GIFTS_KEPT`)만 두고, 타임라인에
  `GIFT`(`actorId` = 받는 사람, `text` = `<job>:<pick>`)를 남긴다. 앱은 이 줄을 버디가 채팅에서 하는 말로 보여 주고(물건은
  그림과 함께, DJ는 방송), 작가의 편지만 `gifts`에서 우편함에 둔다. 독립하면 새 알과 함께 비워진다.
  서버 설정 `buddychat.buddy.gifts`(기본 `false`)가 켜져 있을 때만 연다. 직업 이벤트를 모르는 앱(1.0 빌드 4)은 `GIFT` 줄을 번역 키 그대로
  보여 주므로, 그것을 아는 앱이 EAS Update로 나간 뒤 기본값을 `true`로 바꾼다(`docs/release.md`).

- **채팅으로 돌보기**(`CareCommand`, 앱 `chat-words.ts`와 같은 목록): 메시지 전체가 아래 낱말이면 그 돌봄을 한다. 끝의 "!", `~`, "."는 괜찮고
  문장 안의 낱말은 아니다. 보낸 사람이 한 것으로 처리하고, 메시지는 그대로 남고 메시지 EXP도 받는다.
  - 밥: 밥, 🍚, ごはん, ご飯, 飯, 吃飯, 餵飯, food, feed (중국어는 간체 饭·吃饭도)
  - 청소(한 번에 다 치운다): 청소, 🧹, 똥, 💩, そうじ, 掃除, うんち, 打掃, 清理, 便便, clean, poop (간체 打扫도)
  - 일(어른): 일, 💼, 仕事, しごと, 工作, 上班, work
- **상태는 조회할 때 계산한다**(배고픔·💩은 `lastFedAt`·`lastCleanedAt`과 지금 시각). 스케줄러가 없다.

### 레벨

- 레벨당 EXP는 직업 레벨(`JOB_AT` 10)까지 레벨마다 3·3·3·4·4·4·5·5·5, 그 뒤 10(`BuddyRules.CURVE`, `ExpCurve`). 최고 60(`MAX_LEVEL`). 60이 넘어도 EXP는 계속
  쌓이고 레벨과 바는 멈춘다.
- 단계: 아기 `BABY_AT` 2, 꼬마 `CHILD_AT` 5, 어른 `ADULT_AT` 8. 직업 `JOB_AT` 10, 직업 바꾸기 `JOB_CHANGE_FROM` 20부터 10레벨마다, 독립 `GRADUATE_AT` 60.
- **곡선을 바꿔도 레벨은 그대로**(`BuddyExpScale`): 서버가 시작할 때 `settings`에 기록한 곡선과 다르면 모든 Buddy의 EXP를 같은 레벨,
  그 레벨 안에서 같은 만큼 간 자리로 옮긴다(60을 넘은 EXP는 마지막 레벨의 비율로). 새 곡선을 조건부 update로 먼저 기록하므로 서버 두 대가
  같이 떠도 한 번만 옮긴다. 웹 서버가 열리기 전에 돌아(`SmartInitializingSingleton`, `ApplicationRunner`는 연 뒤라 옮기는 사이 메시지가
  올 수 있다) 1회성 blocking이고, 그래도 읽은 뒤 바뀐 버디(다른 서버가 아직 떠 있을 때)는 다시 읽어 옮긴다. 기록은 직업 전 레벨마다의 EXP(`expBeforeJob`)와 그 뒤(`expPerLevelAfterJob`)다. `expBeforeJob`이 없는 기록은 직업이 Lv.12였을 때의 것으로
  Lv.11까지 모두 `expPerLevel`이고, `expPerLevelAfterJob`도 없으면 모든 레벨이 `expPerLevel`이다. 단계·직업 레벨이 바뀌어도 레벨은 그대로라,
  그때 그 사이에 있던 버디(예: 꼬마였던 Lv.8–9, 직업 없이 Lv.10–11이 된 어른)는 새 단계의 모습이 되고 직업 없는 어른은 첫 직업을 고를 수 있다.

### 둘이 함께

같은 날 두 사람이 모두 메시지를 보내면 하루 한 번 +10(메시지 상한과 별개, 혼자인 방은 없음).

- 메시지마다 보낸 사람을 그날 목록(`talkDay`, `talkers`)에 넣는다. 그날 처음인 사람이면, 목록에 둘이 있고 `togetherDay`가 오늘이 아닐 때만
  주는 조건부 update를 한다.
- 주면 타임라인 `TOGETHER`, 아니면 `buddy` 이벤트만 보내 상대 화면에 누가 왔는지 보인다.
- 독립으로 온 새 알은 그날 기록을 이어받는다.

### 직업

고르지 않고 키운 방식에서 정해진다(`BuddyJob`).

| 직업 | 세는 버릇 | 보통 양 |
| --- | --- | --- |
| 요리사 `CHEF` | 밥 준 횟수(`fedCount`) | 2 |
| 정원사 `GARDENER` | 치운 💩(`cleanedCount`) | 2 |
| 라디오 DJ `DJ` | 밤(23–7시) 메시지(`nightCount`) | 2 |
| 작가 `WRITER` | 사랑 낱말이 든 메시지(`loveCount`) | 1 |
| 바리스타 `BARISTA` | 어느 버릇도 두드러지지 않음 | |

- **판정.** 점수 = 횟수 × 60 ÷ 보통 양. 보통 양은 Lv.10까지 보통 하는 양(둘이 반나절, 혼자 하루쯤)이라, 밥처럼 자주 생기는 일이 횟수만으로
  이기지 않고 다섯 직업이 고루 나온다. 가장 높은 점수의 직업이 되고, 그 점수가 보통의 1.25배(75)에 못 미치면 바리스타. 같은 점수는 버디의 `bornAt`으로
  정한 제비뽑기라 같은 버디는 늘 같다. 보통 양은 실제 분포를 보고 고친다.
- **낱말.** 사랑 낱말은 `buddy/MoodWords`(앱 `chat-words.ts`와 같이 고친다).
- **정하기.** Lv.10에 한 번 `job`을 정한다(`bornAt`이 같고 `job`이 없을 때만). 어른(Lv.8)이 된 모습을 먼저 즐기게 하려고 나눴다. 타임라인은
  `LEVELED_UP`(10) 다음에 `JOB`. 그 전(꼬마, Lv.8–9의 어른)에는 지금까지의 점수로 기울기(`leaning`)만 준다.
- **바꾸기**(`POST …/buddy/job`): 두 멤버 누구든 Lv.20·30·40·50 구간(20–29, 30–39, 40–49, 50–59)마다 한 번, Lv.60부터는 언제든.
  정해진 직업과 합쳐 다섯 직업을 모두 거쳐 볼 수 있다. 바꾼 레벨은 `jobChangedLevel`, 바꿀 수 없을 때 `jobChangeAt`이 다음 기회의 레벨.
  조건부 update 하나(읽은 직업, 그 구간에 바꾼 적 없음)라 동시에 해도 한 번. 타임라인 `JOB_CHANGED`(`actorId` = 바꾼 사람). 점수는 계속 센다.
  직업이 생기기 전부터 있었거나 직업 레벨이 앞당겨져 직업 없이 Lv.10을 넘긴 버디는 언제든 첫 직업을 고르고, 이것은 구간의 한 번으로 치지 않는다.
- **알림(앱).** 대화에는 Lv.10의 직업 카드, Lv.20 카드, Lv.30·40·50의 레벨 업 줄("🔄 직업을 한 번 바꿀 수 있어요"), Lv.60 카드("이제 언제든").
  무대 위 안내(4.5초)는 기회 바로 전 레벨, 기회가 온 레벨, 직업이 정해지거나 바뀐 뒤("다음 직업 바꾸기는 Lv.30부터예요"), Lv.60.
  Buddy 상세는 바꿀 수 없을 때도 회색 자물쇠 버튼("🔒 직업 바꾸기 · Lv.30부터")을 두고, 누르면 규칙과 다음 기회를 펼친다.
- **전직 연출(앱).** 상세에 "🎉 새 직업: 🌱 정원사! 닫으면 무대에서 새 모습을 보여 줘요". 무대는 `jobChanged` 반응으로 진화처럼 빛 고리 속에서 옛 직업과
  새 직업 모습이 번갈아 보이다 반짝이가 터지고, "🎉 새 직업: …!"과 다음 기회 안내, 버디가 "정원사가 됐어!"(`NEW_JOB_LINE`)라고 말한다.
  상세가 무대를 덮는 동안 온 반응은 닫힐 때까지 기다렸다 재생한다(`app/index.tsx`의 `stageReaction`). 상대 화면에서는 바로.
- **직업 값을 바꿀 때**는 저장된 곳(`buddy.job`, 앨범의 `job`, 타임라인 `JOB`·`JOB_CHANGED`의 `text`)을 함께 옮긴다.

### 독립

`POST …/buddy/graduate`, 60레벨(`grown`)일 때만. 지금 버디를 `album`에 push하고 `buddy`를 새 알로 바꾸는 것을 조건부 update 하나로 한다
(같은 `bornAt`이고 60레벨일 때만). 진 쪽은 `BUDDY_NOT_GROWN`. 타임라인 `GRADUATED`, 상대 앱은 room을 다시 읽는다.

| `FED`, `WORKED`, `BATHED`, `TOGETHER`, `JOB`, `JOB_CHANGED`, `GIFT`, `GRADUATED` | 일어날 때 |
| `CLEANED` | 바닥이 깨끗해질 때(마지막 💩) |
| `LEVELED_UP` | 레벨이 오를 때. 단계가 바뀌면 대신 `EVOLVED`, 20이면 `GROWN`, 60이면 `MAX_LEVEL` |
| `HUNGRY`, `POOPED` | 누군가 room을 읽거나 연결할 때, 원인 시각으로 만든 키(`buddy:hungry:<lastFedAt>` 등)로. 메시지 unique 인덱스로 한 번만 남는다 |

진화·레벨 이벤트의 키에는 버디의 `bornAt`이 들어가 새 알이 같은 레벨에 다시 와도 남는다.

### 동시성

- 밥은 `lastFedAt < 지금 - 30분` 조건부 update, 💩은 읽은 `lastCleanedAt`·`poopsCleaned`가 그대로일 때만 바꾼다. 진 쪽은 `changed: false`와 지금 상태를 받는다.
- 일·온천·둘이 함께·직업·독립도 모두 조건부 update 하나라 동시에 해도 한 번이다.
- 변화는 room 전체에 `message`와 `buddy` 이벤트로 간다.

## Room·초대 규칙

### 방 만들기와 초대 코드

- **방 만들기**: room 저장 → `users.roomId: null, roomJoinId: null` 조건으로 연결. 동시 생성에서 연결하지 못한 후보 room은 지운다.
- **초대 코드**: 4자리(0/O, 1/I/L 제외), 24시간 유효, 한 번만, 대소문자 무시.
  - 채팅 앱은 말풍선을 통째로만 복사하는 경우가 많아 손으로 칠 수 있게 짧게 둔다. 참가 화면은 초대 메시지를 통째로 붙여 넣어도 링크에서
    코드를 꺼낸다.
  - 화면과 입력칸에서는 두 글자씩 끊어 `K7 PM`처럼 보인다(`invite-code.ts`, 띄어쓰기는 보기용).
  - 자리마다 글자 종류를 정하면(영어 2 + 숫자 2) 조합이 크게 줄어(31⁴ ≈ 92만 → 약 3만–7만) 그렇게 하지 않고, 입력칸 예시도 그렇게 보이지 않게 섞는다.
  - 짧은 대신 틀린 코드는 이용자당 10분에 10번까지(`INVITATION_RATE_LIMIT`, 서버가 한 대라 메모리에 센다).
  - 만료 1주 뒤 초대 문서를 TTL 인덱스로 지워 코드를 다시 쓴다.
- **초대 링크**: `<웹 주소>/join?code=<코드>`. 웹이 로그인 전에 코드를 기억했다가 이름을 정한 뒤 참가 화면을 연다(`features/room/pending-invite`).

### 참가

- solo room이 있는 사람이 수락하면 `LEAVE_CONFIRMATION_REQUIRED`. 앱이 "지금 Buddy는 사라져요"를 확인받고 `leaveCurrentRoom: true`로 다시
  요청하면 참가하고 기존 solo room은 지워진다. 2명 room의 멤버는 먼저 나가야 한다(`ALREADY_IN_ROOM`).
- **동시성**: 초대 사용(`usedAt: null`) → 사용자 예약(`roomJoinId`) → 참가(`memberCount < 2`) → 예약과 기존 roomId를 확인하며 새 roomId 설정
  → 기존 room 나가기. 진 쪽은 자기 초대 사용과 예약을 되돌린다. 예약 중에는 방 생성도 거절하고, 예약만으로는 새 room에 접근할 수 없다.
  초대에 `previousRoomId`를 남겨 중간 실패 뒤 같은 코드로 다시 수락하면 이어서 끝낸다.
- **참가 알림**: 초대 코드로 빈자리에 들어오면 SYSTEM `MEMBER_JOINED`(text = 들어온 사람 이름)를 남기고 `message`와 `member`를 보낸다.
  - 자리를 넘겨받을 때(`MEMBER_RETURNED`)와 중간에 멈춘 수락을 다시 해 끝낼 때는 남기지 않는다(그 줄은 한 번).
  - 초대한 사람이 3초 뒤에도 그 줄까지 읽지 않았으면 푸시로 알린다(아래 [푸시 알림](#푸시-알림)).
  - 앱은 이 줄만 있는 타임라인을 빈 채팅("○○님과 함께하게 됐어요")으로 보이고, 대화가 시작되면 줄로 보인다. 실시간으로 받으면 무대의
    버디가 기뻐한다(`docs/fun-improvements.md`의 함께 있을 때). 축하 팝업은 두지 않는다.

### 나가기

- 2명 room이면 남은 사람이 room과 Buddy를 갖고 `left`와 SYSTEM `MEMBER_LEFT`(text = 나간 사람 이름)를 받는다.
- 혼자 room이면 room·Buddy·기록이 지워진다.
- 순서는 room에서 빼기(조건부) → 사용자 roomId 비우기(조건부) → 빈 room이면 삭제와 기록 삭제. 다시 나가면 중간에 멈춘 나가기를 끝낸다.

### 다시 초대와 옮기기

다른 앱·브라우저·기기에서 새 사람으로 시작했을 때(계정 연결 없이) 같은 방의 같은 자리로 잇는다. 코드가 누구의 자리인지 `replacesId`에 적는다.

- **상대를 위한 코드**: 상대 이름을 눌러 여는 시트의 "○○님 다시 초대하기". 2명 room에서 만든 보통 코드도 모두 상대를 위한 것이다.
- **나를 위한 코드**: 게스트의 설정 "다른 브라우저에서 내 채팅방 참가"(`self`, "초대 코드로 참가" 바로 위). 예전 곳에서 만들어 새 곳에서 넣으면
  상대 도움 없이 나만 옮긴다. 혼자 방도 된다.
- **확인**: 누군가의 자리를 잇는 코드는 먼저 `SEAT_CONFIRMATION_REQUIRED`(그 사람 이름)로 "○○님으로 이어서 들어갈까요?"를 확인받고
  `takeSeat: true`로 다시 받는다. 내가 상대를 위해 만든 코드를 내가 다른 곳에서 넣어 상대를 밀어내는 실수를 막는다. 그다음 지금 방을 떠나는
  확인이 이어질 수 있다.
- **넘겨받기**: 만든 사람과 그 자리의 사람이 방에 있을 때 한 번의 조건부 update로 `memberIds`의 그 자리를 바꾼다(순서 유지).
  - 같은 자리를 두 코드가 동시에 노리면 하나만 되고 나머지는 `ROOM_FULL`. 상대가 이미 나갔으면 빈자리로 참가하고, 만든 사람이 나갔으면
    `INVITATION_EXPIRED`.
  - 넘겨받은 사람에게 그 방의 상대 메시지(`senderId`)·이름 남긴 기록(`actorId`)·반응·읽음 위치·오늘 대화한 사람(`buddy.talkers`)이 옮겨
    오고, 기록이 바뀌었으니 `historyChanged`. SYSTEM `MEMBER_RETURNED`(text = 새 이름)와 `member`를 보낸다.
  - 예전 계정은 방이 비워지고, 만들어 둔 그 방 코드가 지워지며, 연결된 기기는 `SEAT_TAKEN`으로 끊긴다.
  - 모든 단계는 다시 수락하면 이어서 끝낸다(알림 줄은 한 번).
- 상대의 동의 없이 자리를 넘길 수 있다. 1:1로 아는 사이이고 남은 사람은 원래 대화를 다 보던 사람이라 막지 않고, 예전 기기에 알린다.

## 문의·신고와 상대 내보내기

- 접수는 인증 필요, 내용 1–4000자. 문의는 이용자당 1시간에 5개까지(`SUPPORT_RATE_LIMIT`), 신고·내보내기는 제한이 없다.
- 앱이 만든 UUID `requestId`가 접수 문서의 키다. 같은 요청의 재시도는 이어서 끝내고, 작성자·방·대상·유형이 다르면 `PARTNER_CHANGED`.
- `roomId`·`targetId`가 지금의 방과 상대인지 확인한다. 신고만 최근 TEXT·PHOTO 최대 50개를 복사한다(사진 파일은 방과 함께 지워지고 메일에는 "[사진]"으로 적는다). 접수를 먼저 저장하고 방의 `closureId`를 조건부로
  설정해서 둘이 동시에 요청해도 한 작업만 방을 닫는다.
- 요청자는 새 solo 방 id로 Buddy·앨범을 옮긴다. 대상의 방 포인터, 모든 기존 초대와 예약, 기존 방, 메시지·읽음 위치를 지우고 두 사람의 소켓을
  닫는다. 메시지·읽음·Buddy·소켓 이벤트는 현재 멤버십을 확인하므로 예전 토큰이나 소켓으로 권한이 살아나지 않는다.
- 서버 중단으로 남은 접수는 60초마다 이어서 처리한다. 접수는 `expiresAt` TTL로 90일 뒤 지워진다. 자료를 조회하는 공개 API는 없다.
- 운영자 메일은 Gmail API(`gmail.send`, HTTPS)로 보낸다(호스팅의 SMTP 제한). 60초마다 최대 10건을 임대해 보내고 실패하면 2–60분 간격으로
  재시도한다. Gmail 설정이 없거나 장애여도 접수와 안전 조치는 동작하고 health에는 영향이 없다. 환경변수와 운영은 아래 운영.

## 계정 삭제

App Store Guideline 5.1.1(v) 때문에 있다. 게스트는 Firebase가 30일 뒤 지우지만 서버 데이터는 남으므로 스스로 지울 방법이 필요하다.

- 서버(`DELETE /api/me`, `account/AccountService`): 삭제 진행 표식 → room 나가기 → 내가 만든 초대 → 모든 방의 본인 사진 파일 → 본인 메시지·반응·작성자 정보 → 내 읽음 위치
  → 푸시 토큰 → 사용자 문서 → 표식 순으로 지운다. 단계마다 다시 해도 되는 삭제라 중간에 실패해도 다시 요청하면 끝난다.
- 본인 텍스트·사진과 본인 이름이 든 SYSTEM 기록, 상대 메시지에 단 본인 반응은 예전에 나간 방까지 지운다. Buddy 이벤트는 작성자 id만 지우고 `buddy.talkers`에서도 뺀다.
- 바뀐 방은 `historyVersion`을 올리고 `historyChanged`를 보낸다. 앱은 기록을 비우고 다시 읽으며, 재연결의 `ready.historyVersion`이 달라도 같다.
  삭제 표식이 있는 동안 늦게 저장된 이름 기록·작성자 id도 지우고 그 방을 다시 갱신한다.
- 앱: 연결한 계정은 먼저 다시 로그인한다(Firebase는 최근 로그인 뒤에만 계정 삭제를 허용한다). Apple은 이때 토큰을 취소한다(iOS는
  `accounts:revokeToken`에 인증 코드를, 웹은 `revokeAccessToken`에 access token을 보낸다. 실패하면 서버 삭제 전에 멈춘다). 그다음 서버 삭제 → Firebase `deleteUser`.
  Firebase 삭제가 실패하면 로그아웃하지 않고 알린다. 다시 누르면 서버 삭제는 같은 결과로 끝난다.

## 게스트 정리

서버가 **매주 월요일 04:00(일본 시간)** 정리한다(`account/GuestCleanup`, `@Scheduled`). 서버가 항상 켜져 있어서 가능하고, 두 번 돌아도 같다.

- 게스트 판단: 토큰의 `firebase.sign_in_provider`가 `anonymous`이고 `firebase.identities`가 비어 있으면 게스트.
- 인증된 요청마다 `guest`와 `lastSeenAt`을 적는다(일본 날짜로 하루 한 번까지, 게스트 여부가 바뀌면 바로). `guest=true`는 만들 때만 적고 연결 뒤에는 `false`로만
  바꾼다(연결 전 토큰이 다른 기기에 남아 있어도 되돌리지 않는다). 계정을 연결한 직후 앱이 `GET /api/me`를 한 번 부른다.
- 대상: 게스트이고, 만든 지 30일이 지났고, 7일 동안 요청이 없는 사용자. 지우는 방법은 계정 삭제와 같다. 이 필드가 없는 옛 사용자는 건드리지 않는다.
- 첫 단계에서 사용자가 이미 없는 고아 삭제 표식을 지운다.

## 이용 통계

출시 뒤 어디서 사람이 빠지는지와 다시 오는지를 본다. 사람별 기록은 남기지 않고 날짜별 합계만 `stats`에 올린다(`stats/StatsService`).
날짜는 일본 날짜(한국과 같은 시간대).

- **시작 흐름**: 첫 화면(`welcome`) → 구경하기(`demo`) → 그 안의 시작하기(`start`) → 이름(`name`) → 버디 깨우기(`wake`). 앱이 기기마다
  단계별로 한 번만 보내고(`features/stats/start-steps.ts`, 보낸 단계는 기기에 기억), 서버는 그날·플랫폼의 숫자만 올린다. 대부분 로그인
  전이라 토큰 없이 받으며, 정해진 단계·플랫폼이 아니면 400. 개발 빌드는 보내지 않는다. 초대 코드로 온 사람은 이름에서 바로 참가하므로
  `name`·`wake`에 들어가지 않는다.
- **재방문**: 사용자가 생기면 가입한 날의 `joined`, 다음 날부터 그날 첫 요청이면 가입한 날 문서의 `d<N>`(1–60일째)을 올린다.
  `lastSeenAt`을 하루 한 번 적는 조건부 update와 같은 자리라, 동시에 온 요청도 하루 한 번만 센다.
- **방문자**: 그날 앱을 연 사람 수(`visits:<날짜>`의 `users`, 게스트 포함). 재방문과 같은 자리(하루 첫 요청)에서 올리고 가입한 날도 센다.
  사람별 기록이 없어 주간 순 방문자는 낼 수 없다. 로그인 전에 첫 화면·구경하기만 본 사람은 시작 흐름과 웹 방문(Cloudflare)으로 본다.
- **채팅으로 돌보기**: 밥·청소·일이 실제로 된 횟수를 채팅 낱말(`chat`, `CareCommand`)과 누르기(`tap`)로 나눠 그날 문서에 올린다
  (`BuddyService`의 `counted`). 배부를 때·💩이 없을 때·1시간이 안 된 일처럼 아무것도 바뀌지 않은 것은 세지 않는다. 채팅 낱말을 계속 둘지
  보려는 것이다.
- **보기**: 매주 월요일 09:00(일본 시간) 지난 7일의 날짜별 방문자와 하루 평균, 시작 흐름, 돌보기(채팅 / 누르기)와 최근 6주 가입자의 1·7·30일째 재방문을 문의 메일과 같은 주소로
  보낸다(`stats/StatsReport`). 메일 설정이 없으면 로그에만 남긴다.
- **웹 방문**: Cloudflare Web Analytics(쿠키 없음). Cloudflare가 puny-chat.com 페이지에 비콘을 자동으로 넣으므로 앱에는 코드가 없다.
  대시보드의 Web Analytics에서 페이지·유입 경로·나라를 본다.
- **스토어**: 노출 → 페이지 조회 → 다운로드는 App Store Connect 분석에서 본다.

## 푸시 알림

- **무엇을**: 상대의 새 텍스트·사진 메시지. 제목은 보낸 사람 이름, 본문은 메시지(180자까지, 사진은 기기 언어로 "사진을 보냈어요"). 그리고 서버가 쓰는 안내(게스트의 남은 날,
  친구가 초대로 들어옴 — 초대한 사람에게, 메시지처럼 읽지 않았을 때만):
  기기마다 등록할 때 보낸 앱 언어(`language`, ko/ja/en/zh-Hant)로 쓰고, 언어를 모르는 예전 토큰은 영어.
- **누구에게**: 저장 **3초 뒤에도 그 메시지까지 읽지 않은** 다른 멤버의 모든 기기. 채팅을 보고 있는 앱은 1초 안에 읽음을 보내므로 가지 않는다.
  접속 여부로 판단하지 않는 이유: iOS가 앱을 멈춘 뒤 서버가 끊김을 알기까지 수십 초 동안 접속 중으로 보인다. 전송(ack)은 알림을 기다리지 않는다.
- **앱 푸시**: 앱이 `expo-notifications`로 받은 Expo 푸시 토큰을 등록하고 서버가 Expo 푸시 API로 보낸다(APNs 키는 EAS가 관리). ticket과 약 15분 뒤의
  receipt에서 `DeviceNotRegistered`면 토큰을 지운다(receipt 확인은 메모리 지연 실행이라 재배포하면 빠질 수 있다). 앱이 켜져 있는 동안
  기기 토큰이 바뀌면 앱이 새 토큰을 바로 등록하고 옛 토큰을 지운다.
- **누르면**: 모든 알림이 그 방 이야기라 채팅으로 간다. 설정·도움말에 있다가 나갔어도 채팅으로 돌아오고, 앱이 꺼져 있었으면 채팅으로 열린다.
- **끄기**: 앱 설정의 알림 스위치는 기기별이다. 끄면 그 기기 토큰을 서버에서 지운다. 서버에 사용자별 알림 설정은 없다.
- 설정: `buddychat.push.grace-period`(3s), `receipt-delay`(15m), `expo-access-token`.

### 웹 푸시

- 웹 앱은 `public/manifest.webmanifest`로 설치할 수 있고 `public/sw.js`(서비스 워커)가 알림을 띄우고 누르면 채팅을 연다(열린 창이 있으면 그 창을 앞으로 가져와 채팅으로 옮긴다). 권한은 이용자가 누를 때만
  묻는다(브라우저 규칙): 설정의 알림 스위치나 우편함 편지의 "알림 켜기". 켜면 서버 키로 구독해 등록하고, 끄거나 로그아웃하면 지운다. 앱을 열 때마다 다시 구독한다.
- 아이폰은 iOS 16.4부터, 홈 화면에 추가한 웹 앱에서만 받는다.
- 웹은 알림이 꺼진 채 시작하므로, 알림이 꺼져 있거나(켜기 버튼) Safari라 받을 수 없으면(홈 화면에 추가하는 방법, 게스트면 계정 연결 먼저)
  우편함에 편지가 온다. 켜면 편지가 사라진다. 차단한 경우는 편지와 설정 카드가 브라우저 설정을 안내한다.
- 서버(`notification/WebPush`, `WebPushCrypto`): RFC 8291(aes128gcm)로 암호화하고 VAPID(RFC 8292, ES256)로 서명해 WebClient로 보낸다. JDK 암호화만
  쓴다. 404/410이면 구독을 지운다. endpoint는 알려진 푸시 서비스(FCM, Mozilla, Apple, Windows)의 https 주소만 받는다(SSRF 방지).
- VAPID 키는 Terraform `tls_private_key`(P-256)로 만들어 서버 `.env`에 넣는다. 없으면 실행마다 임시 키(로컬 개발).

### 서버

- Lightsail 인스턴스 `quant-lab-02`(ap-southeast-2, 메모리 2GB + 스왑 2GB, 디스크 60GB, 고정 IP)의 Docker Compose. 파일은 `server/deploy`,
  인스턴스에서는 `/opt/puny-chat`.
- 컨테이너는 둘이다.
  - `server`: 복제 1개(연결·presence·typing이 메모리에 있다). 다른 서비스(quant-lab, ur-check)와 인스턴스를 나눠 쓰므로 힙 `-Xmx384m`(`.env`)·SerialGC,
    컨테이너 640MB로 제한한다.
  - `caddy`: 80/443, 인증서 자동 발급, WebSocket 전달. 컨테이너 256MB.
- 항상 켜져 있어 콜드 스타트가 없다. 배포·재시작 직후의 첫 요청을 위해 앱은 열릴 때 서버를 한 번 깨운다(`lib/warm-up.ts`).
- 서버 설정은 인스턴스의 `/opt/puny-chat/.env`(견본 `server/deploy/.env.example`)에만 있다.
- 사진은 인스턴스 디스크 `/opt/puny-chat/photos`(컨테이너 `/data/photos`, 서버 사용자 uid 1001 소유, `update.sh`가 만든다). 마운트가 없으면
  사진만 `PHOTO_UNAVAILABLE`이 되고 나머지는 동작한다.
- 방화벽은 80·443만 연다. SSH는 Lightsail 브라우저 연결만 허용한다.
- 컨테이너 로그는 `compose.yaml`의 `x-logging`으로 파일 3개(10MB씩)까지만 보관한다(2026-10-21, 모든 컨테이너 로그 합계 30MB를 측정했고 UR Check·모니터링과 같은 값). 다음 배포 때 컨테이너가 다시 만들어지며 적용된다.
- 메모리는 평소 컨테이너를 모두 합쳐 1GB 아래이고 스왑을 오가는 양(`vmstat`의 si/so)이 거의 없어 4GB 요금제로 올리지 않는다.
- `update.sh`가 새 이미지를 받을 때마다 옛 이미지를 지운다. 같은 저장소의 이미지끼리 레이어를 나눠 쓰므로 `docker system df`의 회수 가능 크기는
  실제보다 크게 나온다.

### 배포 파일 맞추기

`server/deploy`는 서버 이미지에 사본(`/app/deploy`)으로 실린다. `update.sh`가 새 이미지를 받은 뒤 인스턴스 파일을 맞춘다.

| 파일 | 맞추는 방법 |
| --- | --- |
| `compose.yaml` | 문법 확인 뒤 `docker compose up -d` |
| `Caddyfile` | 제자리에 쓰고 reload, 실패하면 되돌림 |
| `backup.sh`, `health.sh` | 문법 확인 뒤 새 파일로 바꿔 넣기 |
| `update.sh`, systemd 단위 | 맞추지 않고 손으로 복사한다. 업데이트가 업데이트 장치를 망가뜨리면 스스로 고칠 수 없어서다(다르면 감시가 알린다) |

### DB

- Atlas M0(무료, 512MB, 초당 100 ops), 서버와 같은 시드니.
- 접근 목록은 Lightsail 고정 IP 하나. 비밀번호는 Terraform이 만들어 서버 `.env`에만 두고, TLS로 연결한다.
- 인스턴스를 바꾸면 고정 IP를 옮기거나 `var.server_ip`를 바꿔 다시 apply한다.
- M0는 자동 백업이 없어 인스턴스가 받아 둔다(아래 백업).

### 백업

- **DB 덤프.** systemd 타이머 `puny-chat-backup.timer`(매일 18:00 UTC)가 `backup.sh`를 실행한다. compose의 `backup` 서비스(`mongo:8.0`, profile이 있어
  실행할 때만 잠깐 뜬다)가 `mongodump`로 gzip 아카이브를 `/opt/puny-chat/backups`에 둔다. 매일 것 7개와 일요일 것 3개를 남긴다(가장 오래된 것도 21일 이내).
  Atlas 접근 목록이 Lightsail IP뿐이라 GitHub Actions에서는 받을 수 없다.
- **인스턴스 스냅샷.** Lightsail 자동 스냅샷(매일 18:18 UTC쯤, 최근 7개, 인스턴스를 같이 쓰는 서비스 공용)에 덤프와 사진이 최대 7일 더 남는다.
  인스턴스를 지우면 자동 스냅샷도 사라진다.
- **보관 기간.** 덤프는 스냅샷까지 합쳐 30일, 지운 사진은 7일을 넘지 않는다(개인정보처리방침의 보관 기간). 더 오래 두려면 방침부터 고친다.
- **인스턴스 밖 사본은 두지 않는다.** 인스턴스를 잃어도 운영 데이터는 Atlas에 있고, 인스턴스 침해까지 대비하는 건 이 규모에 과하다.
- **실패 확인.** healthchecks.io가 알린다(아래 감시). 로그는 `journalctl -u puny-chat-backup`.
- **복원.** `/opt/puny-chat`에서:

  ```bash
  docker compose run --rm -T backup sh -c 'mongorestore --uri="$SPRING_MONGODB_URI" --gzip --archive=/backups/daily/<날짜>.archive.gz --drop'
  ```

  운영 DB에 넣기 전에 확인하려면 임시 MongoDB 컨테이너(`--memory 400m`, `--wiredTigerCacheSizeGB 0.25`, `/backups` 마운트)에 넣어 문서 수를 보고 지운다.
  인스턴스 커널(7.0)에서는 `mongod` 8.0이 뜨지 않으므로(SERVER-121912) 이 확인은 `mongo:8.2`로 한다. `mongodump`·`mongorestore`는 클라이언트라
  8.0 이미지로 된다. DB를 인스턴스 안으로 옮길 때도 이 커널에서 뜨는 버전을 쓴다.
- **사진 되살리기.** 스냅샷으로 새 인스턴스를 만들어 `photos`를 꺼낸다.

### 감시

healthchecks.io(다른 서비스와 같은 계정, 알림은 메일)의 체크 세 개에 인스턴스가 신호를 보낸다. 신호가 끊기거나 `/fail`이 오면 알림이 온다.
주소는 인스턴스의 `/opt/puny-chat/healthchecks.env`(견본 `server/deploy/healthchecks.env.example`, Git 제외)에만 있다.

| 체크 | 신호 | 알림이 오는 때 |
| --- | --- | --- |
| `HC_SERVER` | `health.sh`(`puny-chat-health.timer`, 2분마다)가 `https://api.puny-chat.com/actuator/health`(DNS·Caddy·인증서·서버·DB)를 확인하고 성공하면 보낸다 | 세 번 연속(약 6분) 실패하거나 인스턴스가 멈춰 신호가 끊김 |
| `HC_BACKUP` | `backup.sh`가 시작(`/start`)과 성공·실패를 보낸다 | 하루 동안 성공이 없음 |
| `HC_DEPLOY_FILES` | `health.sh`가 이미지의 `/app/deploy`와 인스턴스의 파일·systemd 단위를 비교한다 | 다른 파일이 있음(`/fail`에 파일 이름) |

`HC_SERVER`가 실패할 때 서버 자체도 응답하지 않으면(`/actuator/health/liveness`, DB를 보지 않는다) `server`·`caddy` 컨테이너를 다시 시작한다.
Atlas 장애처럼 재시작으로 낫지 않는 경우는 알리기만 한다. 배포의 재시작은 1분 안에 끝나 알림이 가지 않는다.

### 오류 보고 (Sentry)

- **Sentry Cloud 무료(Developer) 플랜**으로 예상 못 한 오류를 모은다(프로젝트 `puny-chat`, 미국 리전). 서버에 오류 수집 서비스를 직접 두지 않는 것은 2GB 인스턴스를 세 서비스가 나눠 쓰기 때문이고, 무료 한도는 오류 월 5,000건이다.
- **오류만 보낸다.** 대상은 ERROR로 남긴 로그와 처리 안 된 예외(WebFlux 500 포함)다. WARN은 보내지 않으므로 사용자가 알아야 하는 실패는 ERROR로 남긴다(`GuestCleanup`, `StatsReport`, WebSocket 예상 못 한 오류). 트레이싱·로그 수집·breadcrumb은 쓰지 않고, GitHub 저장소도 Sentry에 연결하지 않는다.
- **보내기 전에 줄인다.** 오류 종류·스택·짧은 메시지(300자)만 보낸다. 요청(헤더·본문·쿼리)·사용자·서버 이름은 보내지 않고, 글에 든 이메일·bearer 토큰·URL의 계정 정보는 가린다. 같은 오류(같은 예외 종류, 같은 위치)는 한 시간에 한 번만 보낸다. 구현은 `common/ErrorReporting`·`ErrorReportFilter`.
- **DSN은 인스턴스 `.env`에만 둔다.** 코드·저장소에는 없고, 비우면 SDK가 꺼진다. 릴리스 이름은 이미지를 만들 때 넣은 커밋 sha(`SENTRY_RELEASE`)다.

### 웹 앱과 도메인

- 웹 앱은 Cloudflare Worker의 정적 자산(`app/wrangler.jsonc`). `pnpm build:web`이 `expo export -p web` 뒤 `scripts/worker-assets.mjs`로 404 페이지,
  `_headers`(서비스 워커 no-cache 등), 배포 버전 `version.json`(커밋 sha)을 만든다.
- 홈 화면에 추가한 웹 앱은 새로고침 버튼이 없고 닫아도 멈춰 있을 뿐이라, 앱이 다시 보일 때(1분에 한 번까지) 번들의 버전과 `version.json`을
  비교해 다르면 새로 불러온다(`lib/web-update`).
- 도메인은 Cloudflare Registrar.
  - `puny-chat.com`: Worker. 커스텀 도메인은 wrangler 배포가 붙인다(같은 이름의 CNAME이 있으면 안 된다). Cloudflare가 Web Analytics 비콘을
    자동으로 넣는다(이용 통계).
  - `api.puny-chat.com`: 고정 IP를 가리키는 A 레코드, 프록시 없음, 인증서는 Caddy가 HTTP-01로.
- Firebase 승인된 도메인에 웹 도메인이 있어야 Google 로그인이 된다. 서버 CORS에는 웹 도메인과 로컬 Expo dev 서버.

### Terraform

`infra/`(`infra/README.md`): Atlas 프로젝트·M0·DB 사용자·접근 목록, Cloudflare DNS, VAPID 키. state는 R2, 인증 정보는 `infra/.env`.
Lightsail 인스턴스는 다른 서비스와 나눠 쓰므로 Terraform이 만들지 않는다. 서버 코드는 아래 배포가 올린다.

### CI와 배포

- **CI**(`.github/workflows/ci.yml`): Actions 무료 분을 아끼려고 `dev`로 가는 PR과 `main` push에서만 돌고, 문서·`infra/`만 바뀌면 건너뛴다.
  바뀐 폴더(`app/`, `server/`)의 잡만 돈다. `main`에서는 마지막으로 CI를 통과한 `main` 커밋과 비교한다(취소된 실행의 변경도 검사하도록).
- **배포**(`.github/workflows/deploy.yml`): `main` CI가 통과하면(건너뛴 잡은 막지 않는다) 차례로
  1. 서버 이미지를 GHCR(`ghcr.io/ottuck/puny-chat-server`, `latest`와 sha 태그, 패키지는 Public)에 올린다. 인스턴스가 실행 중인 커밋(`/_revision`)에서
     `server/`가 바뀌었을 때만이다(새 배포는 모든 WebSocket을 끊는다). 수동 실행(`workflow_dispatch`)은 늘 올린다.
  2. 인스턴스의 `puny-chat-update.timer`가 1분마다 `update.sh`로 새 이미지를 받아 컨테이너를 다시 만든다(CI는 SSH로 들어가지 않는다).
     `update.sh`가 실행 중인 커밋을 Caddy의 `/_revision`에 내놓으면, CI는 그 값이 방금 올린 sha가 될 때까지 기다린 뒤 health를 본다.
  3. 웹은 `wrangler deploy`로 바로 올린다.
- **아이폰 앱**(`.github/workflows/app-update.yml`): 배포 뒤 `app/`이 바뀌었으면 EAS Update. 저장소 변수 `EAS_AUTO_UPDATE`가 `true`일 때만(`docs/release.md`).
- **롤백**: 인스턴스에서 `compose.yaml`의 이미지 태그를 이전 sha로 바꾸고 update 타이머를 멈춘 뒤 `docker compose up -d`.
- GitHub secrets: `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `EXPO_TOKEN`. 변수: `EXPO_PUBLIC_*`(빌드에 들어가는 공개 값), `EAS_AUTO_UPDATE`.

### 쓰지 않는 것

- Redis: 레플리카 1개라 메모리로 충분하다. 수평 확장이 필요하면 `RoomHub.publish` 뒤에 Pub/Sub.
- 오브젝트 저장소: 서버가 한 대이고 디스크 여유가 커서 사진은 인스턴스 디스크로 충분하다. 서버가 여러 대가 되면 R2.
- 전용 VM, self-hosted MongoDB, Kubernetes, Kafka.

# 포트폴리오로서

poke-chat(Express + Socket.IO, 익명 글로벌 채팅, 세션 랜덤 ID, Redis 캐시, 재전송 중복)을 새로 설계한 프로젝트다. 보여줄 것: Spring WebFlux로
장시간 연결을 다루는 reactive 서버, WebSocket과 첫 메시지 인증, 재연결과 멱등성, 트랜잭션에 기대지 않는 동시성(조건부 update + unique 인덱스),
presence, 푸시, 모바일 생명주기, 크로스플랫폼.

# 운영

## 문의·신고

공개 연락처는 `support@puny-chat.com`이고, 외부에서 보낸 메일은 Cloudflare Email Routing이 운영자에게 전달한다. 앱의 문의·신고 알림은 서버 `.env`
(Lightsail `/opt/puny-chat/.env`)의 `SUPPORT_EMAIL` 메일함으로 직접 보낸다. 개인 발신·수신 주소는 저장소에 적지 않고 서버 `.env`로만 관리한다.
이용자는 앱에서 접수 완료와 접수 번호를 본다. 개별 이메일 답장, 답장 주소 입력란, 자동 회신, 관리자 페이지는 없다.

### Gmail 연결

호스팅은 SMTP를 막는 경우가 많아(AWS는 25번 포트를 기본 제한한다) Gmail API(HTTPS)로 보낸다. Gmail 앱 비밀번호로는 연결되지 않는다.
운영자 한 계정의 발송 권한만 쓰며, 앱 이용자의 Google 로그인에는 Gmail 권한을 더하지 않는다.

1. Google Cloud 프로젝트에서 Gmail API를 켠다. 운영자 발송용 OAuth 웹 클라이언트를 따로 만들고 승인된 리디렉션 URI로
   `https://developers.google.com/oauthplayground`를 등록한다.
2. [Google OAuth Playground](https://developers.google.com/oauthplayground/) 설정에서 **Use your own OAuth credentials**를 켜고 그 클라이언트 ID·secret을
   넣는다. Playground 기본 클라이언트로 받은 토큰은 24시간 뒤 취소되므로 쓰지 않는다.
3. 권한은 `https://www.googleapis.com/auth/gmail.send`만 고른다. 발송 계정으로 승인하고 authorization code를 교환해 refresh token을 받는다.
   OAuth 앱이 External / Testing이면 refresh token이 7일 뒤 만료될 수 있으므로 Production으로 둔다.
4. 인스턴스의 `/opt/puny-chat/.env`에 아래 다섯 값을 적고 `docker compose up -d`로 컨테이너를 다시 만든다. 인증 값과 개인 메일 주소는 Git·PR·문서에 적지 않는다.
5. 앱에서 문의 한 건을 접수하고 운영자 Gmail에서 접수 번호와 수신을 확인한다.

| 변수 | 용도 |
| --- | --- |
| `GMAIL_CLIENT_ID` | 운영자 발송용 OAuth 클라이언트 ID |
| `GMAIL_CLIENT_SECRET` | 그 클라이언트의 secret |
| `GMAIL_REFRESH_TOKEN` | 발송 계정으로 승인한 refresh token |
| `SUPPORT_FROM` | 승인한 운영자 Gmail 발송 계정. 기본값 없음 |
| `SUPPORT_EMAIL` | 운영자 알림을 받을 메일함. 기본값 없음 |

- 값이 비어 있어도 접수와 신고 조치는 동작하고 메일은 기다렸다가 등록 뒤 보낸다. 실패한 메일은 2–60분 간격으로 다시 보낸다.
  비밀번호 변경·권한 취소·토큰 만료로 승인이 풀리면 다시 연결한다. 서버가 DB 기록 전에 멈추면 같은 알림이 두 번 갈 수 있으니 접수 번호로 확인한다.
- Cloudflare 라우팅 주소는 수신·전달용이라 그것만으로 발송 계정이 생기지 않는다. 발신 Gmail과 전달 대상 Gmail이 같으면 중복 처리될 수 있어
  서버 알림은 메일함에 직접 보낸다. 발송 계정을 바꾸면 발송 변수와 인증 정보를 함께 바꾼다.
- Terraform은 Gmail 변수를 관리하지 않는다. `.env`는 인스턴스에만 있으므로 인스턴스를 다시 만들 때 옮긴다.

### 접수 뒤 대응

- Gmail에서 내용·신고 사유·관련 사용자·접수 번호를 본다. 신고 알림에는 삭제 전 최근 텍스트 최대 50개가 들어 있다.
- 신고가 끝나면 서버가 상대를 내보내고 기존 초대와 두 사람의 대화를 지운다. 신고자는 Buddy·앨범을 갖고 새 solo 방에서 계속 쓴다.
  신고 없는 내보내기는 사본과 메일을 만들지 않는다. 계정 이용 제한은 자동 조치에 없다.
- **24시간 안에 조치한다**(이용약관에 약속한 것). 위반이면 Firebase 콘솔 Authentication에서 그 uid의 계정을 사용 중지한다. 새 토큰을 받을 수 없어
  늦어도 1시간 안에 서비스에서 나가고 다시 로그인할 수 없다. 남은 메시지·방은 Atlas 콘솔에서 지운다(신고하고 내보내기로 신고자와의 대화는 이미 지워져 있다).
- 메일이 오지 않으면 Atlas 콘솔의 `supportTickets`에서 `_id`(앱 접수 번호)로 찾아 `emailStatus=PENDING`, `emailAttempts`, `nextEmailAttemptAt`을 본다.
  본문을 로그나 공개 이슈에 옮기지 않는다. 서버가 정상이면 끝나지 않은 종료 작업도 스스로 다시 한다.
- 접수 기록·신고 사본은 90일 뒤 DB에서 자동으로 지워진다. Gmail의 메일 사본은 지워지지 않으니 대응 뒤 필요 없으면 운영자가 지운다.
  개인정보 요청은 본인 확인 뒤 필요한 범위에서 처리한다.

### 심사 설명에 쓸 사실

초대 코드로 연결되는 최대 2인 텍스트·사진 채팅이며, 공개 피드·사용자 검색·모르는 사람과의 연결이 없다. 다른 사람과 연결하려면 Google·Apple 계정을
연결해야 한다(게스트는 혼자만 쓴다). 모두 처음에 무관용 조항이 있는 이용약관에 직접 동의한다. 서버가 심한 욕설 등을 저장 전에 가린다.
채팅 헤더의 상대 이름과 "문의 및 신고" 화면에서 상대를 신고할 수 있고, 신고와 동시에 대화를 끝내고 상대의 접근·초대와 전체 대화 기록을 지운다(차단).
운영자는 신고 자료를 이메일로 받아 24시간 안에 확인하고, 위반한 계정은 Firebase에서 사용 중지한다. 개인정보처리방침·이용약관과 연락처는 로그인 없이 공개한다.
관리자 페이지는 없다.
